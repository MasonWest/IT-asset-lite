## 零、结论先行

**手册把系统分四层：记录型 → 关系型 → 主动发现型 → 业务协同型。
实况是：前两层已经完成，第三层（主动发现）和第四层（业务协同）一次都没做。**

而手册给的六条实施顺序里，**第⑤条（变更时间线）其实已经做完了**，第③条（地图内联）做了一半。
所以顺序要调，不能照抄。

**我建议的第一刀不是"先把健康检查做出来"，而是「关系核对引擎 + 地图内联」合并成一个切片。**
理由：这两件事共用**同一个派生判断**，拆开做等于把同一段逻辑写两遍 —— 而这个项目已经因为
"两份实现"栽过两次（`useFreeTextOptions` 复制粘贴一次、`hasOwner` 前后端口径分家一次，见决策 50 / 76）。

三条核心判断：

| # | 判断 | 依据 |
| - | --- | --- |
| 1 | **检查引擎必须是纯函数，问题必须是派生的，绝不落库** | 红线 2（派生状态不落库）· 决策 71（四态派生）· 决策 76（`ownership.py` 唯一出处） |
| 2 | **"为什么变成这样"的能力系统已经免费给了** —— 别重做时间线 | `asset_events` + `AssetTimeline.vue`（已覆盖录入/信息变更/状态流转/配对解绑/盘点/换点位） |
| 3 | **迁移功能绝对不能叫 `transfer`** | `/api/transfer` 已经是导入导出的前缀（决策 8） |

### 手册没看到、但现实里已经存在的两块料

1. **地图四态关系层**（v2.2.0，决策 71/72）已经是"关系型系统"的第一次落地 ——

## 二、路线图（分阶段）

排序原则：**先建"能发现问题"的地基，再建"能解决问题"的入口，最后才是"汇总展示"。**
理由同手册 §五 的判断 —— 先做一个漂亮的问题中心，却没有稳定的规则和可靠的问题来源，就是空中楼阁。

```
Phase 0  数据卫生（前置，轻量、可跳过）      ← 只影响"信噪比"，不阻塞
Phase 1  关系核对引擎 + 地图/详情就地呈现     ← 地基，最高性价比（= 手册 ①+③）
Phase 2  迁移助手                            ← 手册 ②（它自己排的最高优先级）
Phase 3  统一问题中心                        ← 手册 ④（视图，不是表）
Phase 4  时间线补口                          ← 手册 ⑤（基本已完成，收尾而已）
Phase 5  管理建议与统计                       ← 手册 ⑥（建立在前面全部之上）
备案     自动配对提示                         ← 条件触发，不排期（见 §五）
```

### Phase 0 · 数据卫生（可选前置）

**做什么**：把 `user_name` 里那批**不是人名**的值处理掉 —— 占位符 `/`、房间名（会议室/前台/大厅/洽谈室）、
以及作为人名使用的 `公用`。

**为什么排在最前但允许跳过**：配对提案量过，真库 **19%（27/143）** 的 `user_name` 不是人名。
任何"把使用人当人比"的规则，遇到这批值都会产生噪音。

**⚠️ 但它不阻塞 Phase 1** —— 因为 Phase 1 的判定表里，
**"写 `/`" 和"留空"都算「未登记」，双方都未登记时不判错**（手册 §三.2 第五行）。
所以引擎天生对占位符免疫，Phase 1 可以先上，数据清洗并行做。

**做什么（具体）**：
- 产出**只读体检清单**（不自动改）：哪些使用人值是占位符/房间名、各几台。
- 清洗方向：会议室类设备**使用人留空、位置填房间名**（位置字段本来就是干这个的）。
- 清洗走既有的**批量导入**（空单元格 = 不修改；想清空写 `-`，决策 5）—— **不写专门脚本**。

**不做什么**：❌ 不建人员字典表（决策 27：自由文本是有意设计，候选会自己长）。
❌ 不做"林晓威 ≈ 林晓薇"的模糊纠错（配对提案 §4.6：误配一次比漏配十次更贵）。

### Phase 1 · 关系核对引擎 + 就地呈现 ★ 第一刀

**这是整条路线的地基。** 它同时满足手册的 ①（健康检查）和 ③（地图内联），因为两者要的是同一个判断。

**做什么**：

| 件 | 落点 | 说明 |
| - | --- | --- |
| 判定口径（纯函数） | `backend/app/services/relation_check.py`（新） | 照手册 §三.2 那张表；**唯一的判定出处**，路由与前端不得各写一份 |
| 只读接口 | `GET /api/insights/relations`（新前缀） | **只读、不写审计**（建议是算出来的视图，不是操作）。`?scope=all` 全库 / `?workstation_id=` 单点 |
| 地图侧栏就地呈现 | `MapStationPanel.vue` | 每台资产旁标「一致 / 需核对 / 未登记」，**不弹窗、不报错色** |
| 资产详情反向呈现 | `AssetDetailView.vue` | 显示"所在点位 + 点位使用人 + 同点位其他资产"，异常项给就地入口 |

**判定表（照抄手册 §三.2，一个字不改）**：

| 点位使用人 | 资产使用人 | 判定 |
| --- | --- | --- |
| 甲 | 甲 | 一致 |
| 甲 | 乙 | **需核对** |
| 甲 | 未登记 | 资产使用人未登记 |
| 未登记 | 乙 | 点位使用人未登记 |
| 未登记 | 未登记 | **不判错**（合法现状） |

**其中「未登记」必须走 `services/ownership.py::has_owner`** —— 空值与 `/`、`／` 都算未登记。
这是决策 76 立的规矩，**新代码不许再写 `(x or "").strip()` 那种判据**。

**为什么这是第一刀**：
1. **零迁移**：数据模型早就支持（`assets.workstation_id` + `workstations.user_name` + `assets.user_name` 三个字段都现成）。
2. **零红线冲突**：纯派生、只读、不落库、不加表。
3. **真数据能立刻触发**：这是唯一一个"今天就扫得出东西"的切片。
4. **它是后面全部功能的地基**：Phase 2 迁移要"复查关系"、Phase 3 问题中心要"问题来源"、Phase 5 建议要"基于真实数据" —— 都调它。

**触发点（关键取舍：静默优先）**：

| 触发点 | 做不做 | 形态 |
| --- | --- | --- |
| 打开地图 / 体检页 | ✅ | 常驻角标，**不弹窗** |
| 单台资产改使用人后 | ⚠️ | **只更新角标，不弹**（单台操作弹窗 = 打扰，决策 63/74 的口径） |
| **批量操作后**（导入 / 迁移 / 批量生成） | ✅ | 结果页**加一行汇总**「本次影响 N 个点位，其中 M 个人员关系需核对 → 去看看」 |
| 迁移后 | ✅ | 强制复查（服务端直接返复查结果，见 Phase 2） |

**验收**：
- 一个**对账脚本**（照 `check_ownership_parity.py` 的路子）：读前端真实源码抠判定表，逐条比对，
  **不在浏览器里复刻一遍引擎逻辑**（自己抄自己，抄错一起错 —— 这是本项目立过的规矩）。
- e2e：地图侧栏角标与接口返回逐点一致。

**不做什么**：❌ 不引入「点位健康分」这种综合指标（不可解释、没法验收）。
❌ 不把"人员不一致"渲染成红色警告（手册 §二.2："异常不等于错误"）。

### Phase 2 · 迁移助手（手册自己排的最高优先级）

**做什么**：把"搬设备"从"改一个字段"升级成**一个完整业务操作**。手册 §三.1 给了五步，照抄：

```
选择迁移对象 → 选目标并预览影响 → 执行前检查 → 确认迁移 → 更新记录并复查
```

**现实里已有的三个原语（别重造）**：
- 资产换点位 = `PUT /api/assets/{id}` 带 `workstation_id`（已可用，已进时间线）。
- 挂/摘资产 = `POST/DELETE /api/workstations/{id}/assets`（已可用）。
- **"移动地图上的点位位置" 与 "把资产搬到别的点位" 已经是两件事** —— 前者是「调整位置」模式（`PATCH /api/workstations/layout`），
  后者改的是 `assets.workstation_id`。**手册担心的"一个『迁移』按钮承载多种含义"在这个代码库里不存在**（决策 44 已经把它们分开了）。

**缺的是什么**：
1. **影响预览**（只读）：当前点位 / 目标点位 / 两边资产清单 / **人员关系差异**（调 Phase 1 引擎）/ 需人工确认项。
2. **整点位业务迁移**这个动作本身（现在没有）。
3. **迁移后复查**：执行完自动跑一次关系核对并把结果返回给界面。

**接口命名（避坑）**：⛔ **不要用 `/api/transfer`**（那是导入导出）。
建议 `POST /api/assets/{id}/relocate`（单台）与 `POST /api/workstations/{id}/relocate-assets`（整点位），
或独立前缀 `/api/moves`。**命名分歧要在写第一行代码前定死** —— 改路由名会波及前端与全部 e2e。

**关键设计（手册 §三.1 原话）**：
> 迁移必须有明确的操作范围，不能因为迁移一个点位，就未经确认地修改所有关联资产的使用人。

→ **迁移只改 `workstation_id`，绝不动 `user_name`。** 人员差异在预览里**列出来给人看**，
但**不自动跟随**。这与 CS 十三.1 那条"刻意不做使用人联动"完全一致 —— 那儿说的是"不一致正是盘点要找的信号"。

**不做什么**：❌ 不做审批流（立项约束）。❌ 不做"迁移即改使用人"的自动联动。

### Phase 3 · 统一问题中心

**做什么**：把各模块发现的问题汇到一个页面（手册 §二.3 那张表：问题 / 来源 / 原因 / 处理入口 / 处理结果）。

**⚠️ 这是全路线最容易踩红线的一步。** 直觉做法是建一张 `issues` 表存"待处理问题 + 状态"，
那**直接违反红线 2**：问题是从数据算出来的**投影**，存下来就会过期（和决策 71 拒掉"点位状态字段"、决策 76 拒掉"拼音列"同一个病）。

**正确形态：问题中心 = 检查引擎的一个视图，不是一张表。**

```
GET /api/insights/issues
  → 引擎现算 → 每条问题带 {source, reason, action_url, action_label}
```

**"处理结果"怎么来**：不存"已解决"状态，而是**事件驱动** ——
用户点"处理"执行了真实操作（补使用人 / 迁移 / 配对），操作本身写 `audit_logs` + `asset_events`，
下次算的时候那个问题**自然就不出现了**。这就是"处理后问题消失"的物理解释，不需要状态字段。

**"例外确认"（手册要求的那条）怎么做**：
手册说"允许管理员确认某种差异是合理的…但例外最好有明确处理记录"。
建议：确认动作**写一条审计**（新增一个 audit action，如 `RELATION_ACK`，带原因），
引擎判定"这条差异是否已被确认"= **该对象最近一条 ack 审计晚于最后一次关系变更事件**（派生）。
**不新增表、不新增状态列。** 代价是新增一个审计动作枚举 —— **这条要你拍板**（审计动作类型是冻结过的清单）。

**为什么排在这**：问题中心是"汇集 + 入口"，它上游必须已经有稳定的规则（Phase 1）和能执行的操作（Phase 2）。
先做它 = 做一个漂亮的待办列表，点进去全是死链。

### Phase 4 · 时间线补口（低成本收尾）

**现状**：`asset_events` 已覆盖 录入 / 信息变更（含换点位）/ 状态流转 / 配对解绑 / 盘点标记。
**手册 §二.5 说的"先盘点已有事件记录的覆盖范围，再补足缺失的业务事件"——
盘点结果是：覆盖得比手册预期好，缺的只有新增动作自己。**

**补什么**：Phase 2 迁移落地后，给迁移**补一个专属事件类型**（现在换点位记的是通用 `update` 的字段差异，
可读性够用但不是一等公民）；Phase 3 的例外确认也要能在时间线上看见。

**不做什么**：❌ **不重建数据模型**（手册自己也这么说）。❌ 不改历史文案（决策 70：审计记录是证据不是文案）。

### Phase 5 · 管理建议与统计

**做什么**：手册 §二.6 那五类问题（长期没绑定的点位 / 没位置的资产 / 需核对的关系 / 频繁迁移的点位 / 一直没完善的资料）。

**全部是可算的**：前三类调 Phase 1 引擎；"频繁迁移"= 对 `asset_events` 按 `workstation_id` 变更频次 group by；
"资料没完善"= `serial_number` 为空 + `warranty_until` 为空这类字段完整度。

**⚠️ 手册的硬要求**：*"这些建议必须基于真实数据，而不是为了让界面显得智能就随意生成结论。"*
→ 每条建议必须能**点开看到构成它的原始记录**，否则就是编的。

## 三、横切设计（比单个功能更重要）

手册 §四 说"这些能力应该共享一套规则和问题处理机制"。落到这个代码库上，具体是四条：

**1. 检查引擎 = 一组纯函数，不是一组服务。**
```
services/relation_check.py   关系核对（Phase 1）
services/data_quality.py     字段完整度 / 重复 / 矛盾（Phase 5）
services/move_impact.py      迁移影响（Phase 2）
→ 都只吃 ORM 对象、只吐结构化结果，不 commit、不写审计、不碰 session 状态
```
理由：可单测、可被多个路由复用、**天然满足红线 2**。

**2. 所有"有没有人"的判断，一律走 `services/ownership.py`。**
新引擎绝不许出现第二份 `(user_name or "").strip()`。这是决策 76 立的规矩，也是本项目最贵的一课。

**3. 用户可见文案与代码标识符继续分家**（决策 70）。
新功能一律用「点位」；代码里 `workstation` / `station` 一个字不改。

**4. 文档税按 14.1 分级表走。**
新阶段默认**只动 CHANGELOG**；只有改了口径（比如"什么算需核对"）才动 CS。别再把"已经发生的事"抄一遍。

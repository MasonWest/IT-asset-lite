## 零、一句话说清它是什么

**问题中心 = 检查引擎的一个视图，不是一张表。**

它要回答三个问题 —— 这也是页面的三段结构：

```
现在有什么值得关注  →  为什么值得关注  →  我能直接做什么
```

```
   数据 (点位 / 设备 / 例外)
          │
          ▼
   services/relation_check.py     ← 已有的关系判定（纯函数）
   services/issues.py             ← 本轮新增：把"问题"组装成统一契约（纯函数）
          │
          ▼
   GET /api/insights/issues       ← 只读，不写审计
          │
          ▼
   InsightsView.vue  ──动作──▶  真实的既有页面（/map?station=、/?workstation=none）
          │                                    │
          └────────── 重新计算 ◀───────────────┘
                 （条件消失 → 问题自然消失；条件还在 → 继续显示）
```

## 一、先定契约：一条「问题」由什么构成

**在写第一行代码前把字段定死**（你给的第 1 条）。每条问题**至少**包含下面 6 项，
**全部由后端下发，前端一个字都不拼**（不许"只为一页临时凑一组文案"）：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `key` | **稳定标识** | `<rule>:<scope>:<对象身份>`，例：`station_vs_asset_user:asset:67`、`asset_unbound:asset:12`。**只由对象身份构成 —— 不含状态、不含时间、不含计数、不含指纹** |
| `rule` | 规则标识 | 用 `RuleKey` 同一套枚举；加规则 = 加枚举 + 加 label，**不在页面里写 if** |
| `severity` | 展示权重 | 复用 `relation_check.Severity`：`ok` / `info` / `review`。**没有 `error` 这个语义** |
| `source` | 来源 | `relation_check` / `data_integrity` / …（对应手册表格里的「来源」列） |
| `object` | 涉及对象 | `{kind, id, code, label}`，复用现有 `Subject`；关系类问题是"点位 + 设备"两个 |
| `reason` | **为什么值得关注** | 一句话，后端给。这决定了页面不是一张冷冰冰的清单 |
| `action` | 可执行动作 | `{kind, label, url}`，**`url` 必须指向一个真实存在、能直接落地的入口**（见 §二 逐条） |

外加一个**可选**的结构化补充（如"两侧分别是谁"）—— **给界面喂字段，别让它解析文案**（v2.5.1 的教训）。

### ⚠️ 稳定标识**不能**拿 `fingerprint` 充数

`Issue.fingerprint` 是**这条关系当下的指纹** —— 它专门用来让例外确认在关系变化后失效，
**关系一变它就变**。拿它当 `key` 的后果：用户改一下使用人，同一条问题就"换了身份"，
去重、定位、跳转、跨页面比对全乱。

**同一条问题里两个字段各司其职**：

| 字段 | 变不变的依据 | 用途 |
| --- | --- | --- |
| `key` | **只随对象身份变** | 去重 / 定位 / 跨页面一致 / 将来扩展 |
| `fingerprint` | **随关系状态变** | 只用于"例外还算不算数"的比对 |

**`key` 与 `fingerprint` 都只是个字符串，问题实体本身不落库。**

### 已被有效例外盖住的差异怎么显示（#1 的配套口径）

真实库里 W61 那 2 处已经被用户确认成例外（理由"公共区域"）。**它不该继续以"待核对"出现，但也不该整个消失**
—— 否则用户不知道"这里有两处是当初特意确认过的"。

口径：

- **不计入待办数**（`counts.review` 不含它）→ 页面顶部说的"有 N 件事值得看一眼"是**真的值得看**；
- 但在该规则卡里多一行：**「其中 2 处已确认为例外（可查看 / 可撤销）」**；
- 这不是"已解决状态"（你给的第 2 条里明令不要的东西）—— 它是**读取例外表这个业务决定记录**的派生结果，
  与决策 80 / P0 卡片的 `handled` 态同一口径。

## 三、明确**不进**问题中心的东西（这是防"红色告警墙"的关键）

你担心"问题中心变成一张越来越长的红色告警清单"。所以**排除项要和纳入项一样明确**：

| 不进 | 理由（都是真实数字，不是我拍的） |
| --- | --- |
| **点位没人 + 挂着有主的设备**（真库 **10 个点位**） | **合法现状** —— 公共设备 / 备用机 / 会议室机器都长这样。P0 的文案里已经明写"这在业务上是正常的"。放进来 = 把正常当异常，**用户会立刻学会无视整个页面** |
| **资料字段缺失**（`serial_number` / `warranty_until` 空：真库 **148 / 148 全空**） | 一进来就是 **148 条**，页面当场变成长清单 —— 正是你说的那堵墙。归 **Phase 5**，且到时要设计成"一类一条 + 批量补录"，不是逐条列 |
| **未配对的显示器**（备案里的自动配对提示） | 路线图给它定的重开条件是"Phase 0 清洗完成 / 录入量明显增大"，现在都不满足。**但引擎留好扩展位**：将来加它只是多一个规则函数 + 一个 `RuleKey` |
| **盘点任务开放太久** | 需要阈值策略（几天算久），属 Phase 5 的"管理建议"（同类还有"长期没绑定的点位""频繁迁移的点位"） |
| **导入时的 warnings** | 只在导入那一刻存在、不落库（红线 2），**不能当问题来源** |

> 一句话原则：**能进来的必须是"值得看一眼的具体对象"**。
> 一类问题如果天然会有上百条，那它不是"问题中心的问题"，是**一批要处理的数据**（Phase 5 的活）。

## 四、接口契约

```
GET /api/insights/issues
  ?rule=<rule>            # 可选：只看某个规则（展开规则卡时用）
  &severity=<review|info> # 可选
  &page=1&page_size=20
```

```jsonc
// 下面用的是**真库的真实数字**（2026-10-15 只读扫出来的），所以它同时是一份"预期结果"参照
{
  "generated_at": "2026-10-15T00:40:00+08:00",
  "total": 32,                                     // = Σ(count - handled_count)，只数"还需要看一眼"的
  "counts": { "review": 0, "info": 32 },           // 不含已被有效例外盖住的
  "by_rule": [
    {
      "rule": "station_vs_asset_user",
      "label": "点位使用人 ↔ 设备使用人",
      "severity": "review",
      "reason": "点位登记的使用人与设备登记的使用人不是同一个人 —— 需要人看一眼，不是错误",
      "count": 2,                                  // 该规则的**全部**问题数（含已确认例外）
      "handled_count": 2,                          // 其中已被有效例外盖住的（count - handled = 计入待办）
      "action": { "kind": "goto", "label": "去地图核对", "url": "/map?station={code}" }
    },
    { "rule": "asset_user_unregistered", "severity": "info", "count": 4,  "handled_count": 0, "…": "…" },
    { "rule": "asset_unbound",           "severity": "info", "count": 28, "handled_count": 0, "…": "…" }
  ],
  "items": [
    {
      "key": "station_vs_asset_user:asset:18",
      "rule": "station_vs_asset_user",
      "severity": "review",
      "source": "relation_check",
      "reason": "…",
      "title": "…",
      "subjects": [
        { "kind": "workstation", "id": 61, "code": "W61", "user_name": "…" },
        { "kind": "asset", "id": 18, "code": "A100-01-xxxxx", "user_name": "…" }
      ],
      "action": { "kind": "goto", "label": "去核对", "url": "/map?station=W61" },
      "fingerprint": "v1:…",
      "handled": true,                             // ← 这条已被确认成例外，所以**不计入 counts.review**
      "exception": { "reason": "公共区域", "created_at": "2026-10-15T00:03:00+08:00", "valid": true }
    }
  ]
}
```

**口径（这几条要进 CS）**：

1. **只读、不写审计** —— 它是算出来的视图，不是一次操作（要求：建议不是操作）。
2. **不新增表、不新增状态列**（红线 2 / 决策 71 / 决策 80 同一条理由）。
   ⚠️ 特别注意：**别建 `issues` 表**，也别给问题加"已解决 / 已忽略"列 —— 存下来必然过期。
3. **排序必须稳定**：`severity desc, rule asc, key asc`。不稳定的话分页会漏条 / 重条，
   而"数量与真实数据一致"这条验收就永远测不准。
4. **`by_rule[].count` 与 `items` 同源**：`count` 是该规则的**总数**，分页不改变它。三个数字的关系写死，免得后面各人各理解：

   | 字段 | 定义 |
   | --- | --- |
   | `by_rule[].count` | 该规则的**全部**问题数（**含**已被有效例外盖住的） |
   | `by_rule[].handled_count` | 其中已被**有效**例外盖住的 |
   | `counts` / `total` | **只数"还需要看一眼"的** = `Σ(count - handled_count)`。已被确认过的不再计入待办，但仍可展开查看 / 撤销 |
5. **实现分层**：规则与组装在 `services/issues.py`（**纯函数**：只吃 ORM 对象、只吐结构化结果，
   不 commit、不写审计、不碰 session 状态，与 `relation_check.py` 同规格），
   路由只负责取数 + 分页。**不许把规则写进路由**（否则无法单测）。
6. **与 `/api/relation-checks` 的分工**：后者是**单个点位的就地呈现**（地图侧栏用），
   前者是**全库汇总视图**。两者**共用同一个引擎**，不重复实现判定。

## 五、前端页面

- **路由**：`/insights`，`meta.title: '问题中心'`；顶部导航新增一项。
- **页面三段**（正好回答三个问题）：

| 段 | 内容 |
| --- | --- |
| ① 现在有什么值得关注 | 一行结论：`2 件事需要核对，32 条提示`。**review 在前**，用琥珀；info 用灰蓝 |
| ② 为什么值得关注 | **规则卡**：标题 + 一句 `reason`（后端下发）+ 数量 + 主入口按钮；`handled_count` 显示成「其中 N 处已确认为例外（可查看 / 可撤销）」 |
| ③ 我能直接做什么 | 展开规则卡 → 逐条：涉及对象 + 原因 + 动作按钮（跳到真实页面） |

- **空状态不许是一片空白**：明写"**检查了 N 条规则、69 个点位、148 台资产，现在没有需要处理的关系问题**"，
  并列出**检查了哪些规则**。"干净"是一个结论，要让人看见它是被查出来的。
- **配色沿用 P0 口径**：`review` 走**琥珀**、`info` 走**灰蓝**，**不用红色** —— "异常不等于错误"。
- **不做常驻红点角标**（见 §十二 待拍板 2）。
- **动作必须落到真实页面并带定位参数**。为此需要给 `/map` 加一个 `?station=<code>` 支持 ——
  它**已经在用这套 query 约定**（`SpaceMapView.vue` 的 `?task=`，读在 :490、写在 :1323），
  这是本方案**唯一一处存量页面的改动**，改动面很小。

## 七、Phase 4 · 时间线补口（随本轮，复用现有机制）

### 1. 迁移配一个专属事件类型

- 新增 `AssetEventType.RELOCATE = "relocate"`，LABELS 加「点位迁移」；
- `routers/relocation.py::_apply_moves` 把现在的 `AssetEventType.UPDATE` 换成它
  （现在迁移在时间线上长成通用"信息变更"，可读性够但不是一等公民）；
- 前端 `utils/format.ts::EVENT_META` 加一条 + `EVENT_TYPES` 联合数组加 `'relocate'`。

> 风险很低：`eventMeta()` **有兜底**（未知类型渲染成灰点），`AssetTimeline.vue` 的筛选条是
> **从返回数据现生成**的 —— 新类型会自动多出一个 chip，不需要改时间线本身。

### 2. 例外确认进时间线

confirm / revoke 时给**对应那台设备**补一条 `asset_events`（新类型 `relation_exception`）。
这样"这台设备的使用人差异曾被确认为合理（理由 X）"在它的履历里看得见 ——
否则看履历的人完全不知道这段历史。

**两条边界要写死：**

- ⚠️ **只覆盖 `scope=asset` 的例外**。点位级例外（`asset_id=0`）没有对应的设备，
  写不进 `asset_events` —— 它在**点位侧栏**呈现（P0 已有），不硬塞。
- ⚠️ **"例外失效"不写事件**。失效是**算出来的**（指纹比对），落库就违反红线 2。
  时间线上有"确认"而没有"失效"是**正确的**，不是漏了。**别顺手补一条"失效事件"。**

**不做**：不重构时间线、不改历史文案（决策 70：审计与事件记录是证据，不是文案）。

## 八、markStation · 单排（本轮明确不做）

要改的是**审计口径**：现在一键把整个点位标为已盘 = 逐台循环调接口 = **N 条 `inventory_mark` 审计**，
与"一次批量操作 = 1 条审计"相悖（批量导入 / 迁移都是 1 条）。

单排的理由：它是口径变更，要先定清楚 ① 事务边界、② 部分失败是整体回滚还是逐台跳过、
③ 审计模型（是"1 条批量"还是"1 条批量 + 每台 1 条 `asset_events`"—— 迁移已经是后者，可复用同一套）。
**塞进本轮会让 Phase 3 的"数量与真实数据一致"这条验收凭空多一个变量。**

## 十、验收清单（你给的 5 条，逐条落到可执行断言）

**第 5 条的展开（这条最容易做成"看起来绿"）：**

  - 关系类 → 逐点位调 `GET /api/relation-checks/workstation/{id}` 汇总 `review_count`；

  - 已删点位 → 只读 SQL 直接查。
  ⚠️ **不写死任何条数**（用户自己会加点位、确认例外）—— 能对账就对账，条件不成立就 `exit 2`。

  问题中心的 e2e 要么**自带造数据**，要么把前提做成可跳过的分支。

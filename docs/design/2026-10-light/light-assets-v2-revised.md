## 0. 这一版改了什么，为什么

第一版是**按"把轻资产做成一个小型 ERP 台账"的思路**设计的：给品类加 `tracking` 双模式、

给单件建独立档案、所有当前状态一律从流水重放推导。三个决定各自都有道理，合起来却偏离了实际业务：

| 第一版的做法                | 实际业务里并不需要                              | 代价                                    |
| --------------------- | -------------------------------------- | ------------------------------------- |
| 品类分「按数量 / 按单件」双模式     | 我们不追轻资产 SN，正式资产也没全面登记 SN               | 两套并行逻辑，界面要用户先选模式；单件表、单件详情、单件历史全是额外负担  |
| 单件独立建档（`light_items`） | 同上 —— 记"2 条内存装在 A100 上"就够，不需要给每条内存一个身份 | 建了档却"未登记"的空档案没人看得懂（上一轮真实发生过）          |
| 当前状态 100% 由流水实时重放     | 心算是可以的，但每次列表查询都要把该品类全部流水读出来遍历          | 台账页 20 个品类 = 上百次查询；且"改错一条流水"要等下次查询才反映 |

这一版按你给的方向重做，核心是**回到"品类 + 数量 + 当前分配记录 + 流转历史"**&#x8FD9;一件事上。

### 与你 6 条约束的逐条对应

| 你的约束                   | 本方案怎么落实                                                      | 落在哪一节       |
| ---------------------- | ------------------------------------------------------------ | ----------- |
| 1. 取消双模式，统一按品类+数量管理    | 删 `tracking`、删 `light_items`；SSD 也按数量管，用"分配记录"记它装在哪台资产上      | §1.1 / §3   |
| 2. 明确当前归属，禁止互相冲突的位置    | 新增 `light_holdings`，**一条记录只有一个持有位置**（四选一）；使用人不与资产/点位并存       | §1.2 / §3.2 |
| 3. 复用现有点位与地图，不做第二套位置体系 | 不新增任何位置表；点位用 `workstations`，地图不建轻资产对象，只在点位/资产详情加区块           | §5          |
| 4. 简化库存初始化             | 期初确认建立上线基准、**但允许补录与调整**；历史 Excel 只补流水；**须维护库存但不建复杂仓储**（决策 2） | §6          |
| 5. 不强制纯派生，可维护当前状态      | `light_holdings` 与流水**同事务双写**，以流水为准、可重建，配一致性自检               | §4          |
| 6. 先出方案不改代码            | 本文档就是产出物                                                     | 全文          |

## 1. 三个核心对象各管什么（对应问题 1）

### 1.1 `light_categories` —— 品类：回答"这是什么"

一句话职责：**一类东西的定义**。名称、品牌（选填）、规格（选填）、单位。

明确**不做**的事：不记数量、不记位置、不记追踪模式。它就是一张字典表。

> **删掉 `tracking` 是本轮最重要的减法。** 它当初存在，是为了决定"要不要为每件东西建档"。
>
> 现在既然统一按数量管，这个开关没有任何存在理由，
>
> 留着只会让界面继续问用户一个他不需要回答的问题。

### 1.2 `light_holdings` —— 当前分配记录：回答"现在在哪、有几件"

一句话职责：**把"这个品类当前分布在哪些位置、各多少"直接落库**。

这是本轮新增的一张表，也是整个模块的"当前状态"载体。每条记录 = 一个持有位置 + 该位置上的数量。

**关键约束（就是你说的"位置明确且不重复"）**：一条记录**只能有一个持有位置**，四选一：

| `holder_kind` | 什么时候用          | 现实例子                      |
| ------------- | -------------- | ------------------------- |
| `asset`       | 装在某台正式资产上的配件   | 2 条内存插在 `A100-03-00001` 上 |
| `workstation` | 固定放在某个工位用的     | 1 套键鼠放在 `W23` 工位上         |
| `user`        | 专门发给某人、没有固定位置的 | 3 套键鼠发给张三（他跑多个工位）         |
| `stock`       | 还没分配出去，在库房     | 5 个转接头备着                  |

**使用人不是第五种位置，而是展示信息。** 这正是你点出的那个问题：

> 人员可作为使用人信息展示，但不能仅凭人员关系推断配件所在点位，因为一个人可能涉及多个点位。

所以规则是：

- 持有位置是 `asset` / `workstation` 时，**使用人一律现读宿主**（`assets.user_name` / `workstations.user_name`），

  本表**不另存一份**。主机换人，配件跟着变，不需要改两遍。
- 持有位置是 `user` 时，记录上**不带任何点位**，界面就老实说"在某人手上，未记录固定位置"。

  **绝不**因为张三名下有个工位，就推断这套键鼠在 W23。
- 一个品类**可以有多条**持有记录（库存 5 + 张三 2 + A100 3），这是正常的分布；

  "不冲突"指的是**每一条记录只有一个位置**，不是整个品类只有一个位置。

### 1.3 `light_movements` —— 流转流水：回答"怎么变成现在这样的"

一句话职责：**append-only 的历史**。每一次归属变化追加一条，永不修改。

它与 `light_holdings` 的分工是"过去"与"现在"：

- `light_holdings` = 现在的快照，给列表页和详情页直接读（快、简单）；
- `light_movements` = 完整轨迹，给"这条 SSD 去年装在哪台机器上"这种问题（全、可审计）。

**为什么两者都必须有，而不是二选一**：

- 只要流水 → 每次查列表都要重放全部历史（第一版的性能问题）；
- 只要 holdings → "从张三转给李四"这段过程消失，你要求的"关联关系变化时保留完整历史流水"做不到。

## 2. 当前归属对象的数据结构（对应问题 2）

### 2.1 表结构

```
light_holdings                        -- 当前分配记录（"现在在哪、有几件"）
  id                INTEGER PK
  category_id       FK light_categories  RESTRICT, NOT NULL
  holder_kind       VARCHAR(16)  NOT NULL   -- stock / user / asset / workstation（四选一）
  asset_id          FK assets       RESTRICT, NULL       -- kind=asset 时必填
  workstation_id    FK workstations RESTRICT, NULL       -- kind=workstation 时必填
  holder_user       VARCHAR(64)  NULL                    -- kind=user 时必填，自由文本
  stock_location    VARCHAR(128) NULL                    -- kind=stock 时的存放位置描述（见 2.4）
  quantity          INTEGER      NOT NULL, > 0
  since             DATETIME     NOT NULL   -- 这一条是从什么时候开始的
  note              VARCHAR(255) NULL
  created_at / updated_at
```

### 2.2 "位置明确且不重复"靠什么保证

分四层，从数据库到界面逐层收口：

**第一层 · 应用层校验（写库前）**——与全站口径一致（项目不用 DB 级 CHECK，见 `asset_relations` 的注释：跨库兼容性）：

- `holder_kind` 与引用字段必须**严格对应**：`asset` → 必须有 `asset_id` 且其余三个为空；

  `workstation` → 必须有 `workstation_id` 且其余为空；`user` → 必须有 `holder_user` 且其余为空；

  `stock` → 三个都为空。不符合就 400。
- `holder_user` 走 `services/ownership.py::has_owner()` —— `/`、空串这些占位符不算人（复用既有实现，不重写判断）。

**第二层 · 唯一约束**（防止同一位置冒出两条记录）：

```sql
-- 部分唯一索引：SQLite 支持（PostgreSQL 也支持）
CREATE UNIQUE INDEX uq_light_hold_asset
  ON light_holdings(category_id, asset_id)       WHERE asset_id IS NOT NULL;
CREATE UNIQUE INDEX uq_light_hold_station
  ON light_holdings(category_id, workstation_id) WHERE workstation_id IS NOT NULL;
CREATE UNIQUE INDEX uq_light_hold_user
  ON light_holdings(category_id, holder_user)    WHERE holder_user IS NOT NULL;
-- 库存按"存放位置"而不是按品类唯一：同一个品类可以分放几处库房
CREATE UNIQUE INDEX uq_light_hold_stock
  ON light_holdings(category_id, COALESCE(stock_location, ''))
  WHERE holder_kind = 'stock';
```

> ⚠️ **这里的口径随决策 4 调整过一次，需要说明**：
>
> 初稿把库存约束写成 `(category_id, holder_kind) WHERE holder_kind='stock'` —— 即"一个品类只能有一条库存记录"，
>
> 那样库存就是一个**无法定位的抽象数字**，不符合"库存也应能表达实际存放位置"。
>
> 改为按 `stock_location` 唯一后：一个品类可以有几条库存记录（如"库房A 3 个""前台抽屉 2 个"），
>
> 但**同一存放位置不会出现两条**。`COALESCE(...,'')` 是为了让"没填位置"本身也成为一个可唯一的取值。

> ⚠️ 这里与 `asset_relations` 的取舍**故意不同**，需要说明理由：
>
> 配对表不建唯一索引，是因为它要保留"解绑"的历史行（`active=0` 的行不能互相冲突）。
>
> 而 `light_holdings` **只存当前状态、不存历史** —— 历史在流水里。
>
> 表里没有软删行，所以部分唯一索引不会误伤任何合法数据。
>
> 这也正是"拆成 holdings + movements 两张表"带来的一个具体好处。
>
> 注意 SQLite 与 PostgreSQL 都支持部分唯一索引（`WHERE` 子句）；MySQL 不支持 ——
>
> 这是本项目明确不打算支持的库（约束里写的是 SQLite，将来换库只改 `database.py` 连接串）。
>
> 若将来真要迁 MySQL，退路是"应用层校验 + 普通唯一索引"，已记在 §9 风险里。

**第三层 · 派生视图的自洽**（防止界面显示矛盾）：品类列表上的"库存 / 已分配"不再独立计算，而是

`light_holdings` 直接聚合：

```
库存(品类)   = Σ quantity WHERE holder_kind='stock'
已分配(品类) = Σ quantity WHERE holder_kind IN ('user','asset','workstation')
```

两者都只读同一张表，**结构上不可能对不上**。这直接消灭了上一轮实测出的那个"账面凭空多出 3 套"的缺陷

（当时"库存"走流水聚合、"持有明细"走另一条除法再过滤负数，两处口径不一致）。

**第四层 · 界面层**（不给用户制造歧义）：登记流转时**不再让用户同时选"来源类型"和"去向类型"**，

而是选业务动作（发给某人 / 装到机器 / 换手 / 收回 / 报损），位置由动作唯一确定（见 §4.3）。

### 2.3 为什么不用"使用人 + 点位都记"这种更灵活的设计

看起来更"全"：一条记录既能记"给张三"，又能记"在 W23"。但这正是你要求避免的东西 ——

它会立刻产生一个无法回答的问题：**张三调去别的工位了，这条配件跟着走还是留下？**

系统的答案是：这两个事实本来就不该由同一条记录同时表达。

- 配件**跟着人走** → 记 `user`；
- 配件**固定在工位** → 记 `workstation`。

需要"人在哪、东西也在哪"这种关联时，看的是 `assets.user_name` 与 `assets.workstation_id`（正式资产已经维护了这层关系），

轻资产只是搭在正式资产上现读，不自己再造一套。

### 2.4 库存也要能定位（决策 4 新增）

库存**不能是一个无法定位的抽象数字**。所以 `stock` 这一类带一个 `stock_location` 文本字段：

- 可以是自由描述（"3 楼库房 A 柜"、"前台抽屉"）；
- **也可以是某个点位的编码**（"W01"），表示东西就放在那个闲置点位上。

为什么这里是自由文本、而不是外键指向 `workstations`：现实里备件常放在**不是工位的地方**

（库房、机柜、行政抽屉）。强行要求先在地图上建一个点位才能登记库存，会把"库房"这种不存在于

工位图的空间硬塞进点位表，污染地图。允许填编码时，展示层会尝试匹配同名点位并做成可点击链接。

**它不参与守恒计算**（数量才是），只回答"这批备件在哪"。

## 3. 数量怎么算：分配、部分归还、更换、转移、报损（对应问题 3）

### 3.1 统一模型：一次操作 = 两个持有记录上的加减

所有操作都表达成"从 A 位置减 q，往 B 位置加 q"：

```
apply(from_holder, q, -1)    -- 来源位置数量 -q；减到 0 就删掉这条记录
apply(to_holder,   q, +1)    -- 去向位置数量 +q；不存在就新建
```

于是每种业务动作只是 (A, B) 的不同组合：

| 业务动作  | A（来源）   | B（去向）        | 数量守恒  |
| ----- | ------- | ------------ | ----- |
| 入库    | —（系统外部） | stock        | 总量 +q |
| 期初确认  | —（系统外部） | 任意位置（可一次写多条） | 总量 +q |
| 分配给人  | stock   | user         | 不变    |
| 安装到资产 | stock   | asset        | 不变    |
| 放置到点位 | stock   | workstation  | 不变    |
| 转移/换手 | 任意位置    | 任意位置         | 不变    |
| 归还/收回 | 任意位置    | stock        | 不变    |
| 报损    | 任意位置    | —（系统外部）      | 总量 −q |

### 3.2 逐个说明

**分配（stock → user / asset / workstation）**

前置校验：来源位置的 `quantity ≥ q`，否则 409 + 人话（"库存只有 2 套，不能发出 3 套"）。

扣减来源、增加去向。归属变化在流水里留一条。

**部分归还（user → stock，q 小于持有量）**

这不是特例，就是上面的通用算法：来源记录 `-q`，若减完仍 > 0 就只更新数量；

减到 0 才删除该条记录。**"部分"与"全部"走同一条代码路径**，不需要两套逻辑。

**更换（旧件报废 + 新件顶上，一次操作完成）**

业务场景：A100 上那根 8G 内存坏了，换一根新的，人（和机器）都没变。

设计为**一条业务操作、两条流水**，同一个事务里完成：

1. `报损`：`asset(A100) -1`（旧件退出管理）
2. `安装`：`stock -1 → asset(A100) +1`（新件装上）

为什么不分两次让用户点：中间那一下如果只做了一半（旧件已报损、新件还没装），

账上会短暂出现"这台机器少一根内存"，而实际并没有。一次事务提交，要么都成、要么都不成。

界面上仍呈现为**一个**"更换配件"动作，用户不需要理解背后是两次物料移动。

**转移（任意位置 → 任意位置）**

人与人的转移（张三 → 李四）、机器与机器的转移（A100 → A101）、人与机器相互转移，

都是同一条算法。**专门覆盖你上一轮发现的问题**：以前"张三那 2 套改归李四"只能绕

"归还 + 分配"两步，一次换手被记成两次出入库，时间线上看不出是同一批东西换了人。

**报损（任意位置 → 系统外部）**

从 A 位置 `-q`，总量 `-q`。报损后的东西**不能再走"入库"复活**（上一轮已修）；

误报损走 `调整（盘盈）`，时间线上留下的是"调整"而不是"入库"，

因为"盘点时又找到了"和"新买了一套"是两件事。

### 3.3 守恒与校验

- **守恒式**：`Σ holdings = Σ(入库 + 期初 + 盘盈) − Σ(报损 + 盘亏)`。

  每次写操作后断言这条式子，破了就整体回滚（不是记个日志了事 —— 那说明代码有 bug）。
- **不允许任何位置的数量为负**：所有减操作先校验 `quantity ≥ q`。
- **不允许数量为 0 的记录留在表里**：减到 0 即删除，避免"0 件的持有记录"污染列表与统计。
- **不允许计数重复**：`(category_id, holder_kind=stock)` 唯一（见 §2.2 第二层）。

## 4. 当前状态与流水的关系（对应问题 5）

### 4.1 双写，但只有一个"真相"

你明确说不强制纯派生。本方案采用：

- **`light_holdings` 是查询用的快照**（列表页、详情页直接读它，不重放历史）；
- **`light_movements` 是可重建快照的唯一依据**（audit / 历史查询 / 出问题时重建 holdings）；
- 两者**在同一个事务里写入**：改 holdings、追加 movement、写 audit，一起 commit，任何一步失败整体回滚。

### 4.2 如何保证两者一致（这是双写方案唯一的风险点）

\*\*口径已按决策 1 确定：接受"单一业务入口 + 同事务双写 + 体检脚本 + 可重建"，

但体检与重建是额外保障，不能反过来替代事务一致性。\**

**① 单一业务入口（保证正确性的主路径）。**

holdings 只允许被 `services/light.py::apply_holding_delta()` 修改，

不暴露任何"直接改 holdings"的接口（与全站"没有直接改库存的操作"口径一致）。

所有业务动作都必须经由这一个函数，它内部**同时**改 holdings、追加流水、写审计，

**在同一个数据库事务里完成**：

```
begin
  apply_holding_delta(from_holder, -q)     -- 来源扣减（减到 0 即删行）
  apply_holding_delta(to_holder,   +q)     -- 去向增加（不存在则新建）
  record_movement(...)                     -- 追加流水
  record_audit(...)                        -- 追加审计
  assert_conservation(category)            -- 守恒断言，破了就 raise
commit                                       -- 任何一步抛错 → 整体回滚
```

**决策 1 明确禁止的做法**：拿"反正有体检脚本和重建工具"当理由，

放宽事务边界（比如先写 holdings 再异步补流水、或分两次 commit）。

体检是**发现**问题的，不是**允许**问题的。

**② 一致性体检脚本（只检查，不自动修复）。**

对每个品类，把流水重放一遍算出应有的 holdings，与实际 `light_holdings` 逐条比对，报告差异：

- 数量不一致（表里多少 vs 重放算出多少）；
- 表里有、重放算不出来的"幽灵持有"；
- 重放算得出来、表里却没有的"漏记持有"；
- 任何位置出现负数；
- 守恒式不成立；
- 流水里引用了已被删除的资产/点位（应回落到编码快照，不算错，但要列出提示）。


**行为约束（决策 1 硬性要求）**：

- **默认且唯一的常规模式就是"只检查"**，输出报告，**绝不自动改数据**；
- 脚本**不提供 `--fix` 直接修库的开关** —— 修复动作与检查动作分离（见 ③）；
- 报告要能直接看出"差在哪条记录、差多少、涉及哪个品类"。

**③ 重建（先出差异报告，确认后才执行）。**

重建 = 按流水重新算出 holdings 并覆盖。它比体检危险，所以流程被拆成两步：

1. **`--report`（默认）**：只输出"重建后会发生什么"的差异报告 ——

   哪些记录会被新增、哪些会被改、哪些会被删，逐条列出**改前 → 改后**。
2. **`--apply --confirm`**：在**先备份库**（复用 `backend/backup_db.py`，含完整性校验）之后才真正写入；

   没有显式确认参数一律不写。

这样避免"重建工具把当前正确的状态覆盖成错误状态"——因为人在覆盖前已经看过差异。

**④ 重建必须知道哪些流水有效（这是决策 1 与"重点把握第 2 条"共同强调的点）。**

⚠️ **绝不能把全部流水简单相加。** 三类来源的参与规则不同，重建工具必须严格按这张表执行

（复用 `models.py::LightOrigin.EFFECTIVE` 的既有定义，**不在脚本里另写一份判断**）：

| `origin`  | 含义          | 参与重建       | 原因                                    |
| --------- | ----------- | ---------- | ------------------------------------- |
| `manual`  | 日常业务流转      | ✅          | 就是当前状态的来源                             |
| `opening` | 期初确认 / 盘点调整 | ✅          | 建立的是真实基线                              |
| `import`  | 历史 Excel 导入 | ❌ **绝不参与** | Excel 里只有分配、没有对应入库；算进来会得到负库存或凭空出现的持有量 |

还有两条容易漏掉的规则：

- **冲正流水参与**（`corrects_id` 不为空的那条也是有效流水）—— 冲正本身就是一次真实的归属变动；

  重放时按时间顺序把原记录和冲正记录**都**算进去，结果自然抵消，不要特殊处理；
- **排序必须稳定**：按 `occurred_at ASC, id ASC` 重放（同一时间多条时用 id 兜底），

  否则同一天的"分配 + 归还"重放顺序不同会得到不同结果。

脚本必须支持 `--dry-run` 打印"本次参与计算的流水条数 / 被排除的 import 条数"，

让人一眼确认口径没跑偏。

**⑤ 重建能力作为兜底（不是主路径）。**

因为 holdings 本身可以从流水完整重建，"表被写坏了"不是灾难 —— 但如上所述，

**重建必须先出差异报告、必须备份、必须显式确认**，它是事故恢复手段，不是日常操作。

### 4.3 界面层的收口（顺带解决"用户不知道该点哪个"）

登记流转从"来源类型 / 去向类型"两个技术下拉，改成**先选业务动作**：

> 入库 / 建期初库存 ｜ 发给某个人 ｜ 装到某台机器 ｜ 放到某个点位 ｜ 换个人 / 换个地方 ｜ 收回库存 ｜ 报损

用户只回答"给谁""哪台机器"；`(holder_kind, 引用字段)` 由动作唯一确定，

界面不给他机会组合出"使用人 + 点位"这种冲突状态。提交前给"操作前 → 操作后"确认条，

**不变的行显式标"不变"**。

## 6. 期初确认与历史导入怎么区分（对应问题 6）

这两个东西长得很像（都是"一次性录入一批数据"），但性质完全不同。区分不好会直接导致**账目失真**，

所以本方案用最明确的方式把两件事分开。

### 6.1 期初确认（`origin='opening'`）

**定义**：上线时做**一次**的盘点确认 —— 建立"此刻真实有什么、都在哪"的基线。

**它的定位（按决策 2 修正）**：

- 上线时**建立基准**，把"此刻真实有什么、都在哪"一次性登记清楚；
- 计入当前状态：直接建立 `light_holdings`（库存 X 件、张三 Y 件、A100 上 Z 件）；
- 同时写对应的流水（`origin='opening'`），这样基线本身也可审计、也能被重建；
- **必须填操作人** —— 一份没人认领的基线等于没建立（沿用既有校验）。

⚠️ **期初不是永久封锁**（决策 2 明确要求，此处是初稿写错、已改）：

初稿写的是"只做一次，不留再来一次的后门"，这会造成一个真实的问题：

上线后发现漏录了一个品类、或盘点发现数量不对时，

`schema_meta` 已经标记"初始化完成"，用户就只能想办法绕过系统 —— 那是最坏的结果。

改为：

- `schema_meta` 里的标记**只是"提示用"**，含义是"这个品类做过期初了，界面不必再催"，

  **不是"禁止再录入"的开关**；
- 期初确认**允许重做**（如漏了整个品类补做一次）；
- 日常的库存修正走**有审计记录的盘点调整**（`adjust`，盘盈 / 盘亏），

  这是正常业务动作，随时可用，不受任何"已初始化"标记限制。

**区分"补录"与"重复初始化"**：反复做无意义的初始化会让基线失去意义，

所以界面上的措辞是"按实际盘点结果登记期初"而不是"初始化"，并且每次都会留一条带操作人的流水；

真做了几次，历史里看得见，不会悄悄发生。

**界面上怎么表达**：品类还没做过期初确认时，详情页显示一条中性提示 + 一个按钮

（"按实际盘点结果登记期初"）；做过之后这条提示收起来（但不禁止再次登记）。

### 6.2 历史导入（`origin='import'`）

**定义**：把以前 Excel 里的记录补进系统，**只补历史事件**。

**它做什么**：

- **只写 `light_movements`，绝不碰 `light_holdings`**；
- **不计入任何当前状态**（不参与库存、不参与已分配、不参与守恒式）；
- 天然去重：同一份 Excel 导两遍，第二遍是 0 新增（按自然键查重）；
- 导入结果是"可查的历史"，不是"现在的账"。

**为什么必须这样**：Excel 里通常只有"某年某月把这套键鼠给了张三"，

没有对应的入库记录。如果把这些直接当当前状态，会得到负库存或凭空出现的持有量 ——

上一轮实测出来过。所以：

> **历史导入后，当前状态仍是空的**（除非另外做了期初确认），
>
> 台账上显示"未登记入库"而不是猜一个数字。这是诚实，不是缺陷。

### 6.3 两者的对照表

| 维度                  | 期初确认 `opening`              | 历史导入 `import`        |
| ------------------- | --------------------------- | -------------------- |
| 目的                  | 建立**现在**的基线                 | 补**过去**的事件           |
| 写入 `light_holdings` | ✅ 是                         | ❌ 绝不                 |
| 计入当前状态              | ✅                           | ❌                    |
| 参与守恒式               | ✅                           | ❌                    |
| 参与重建重放              | ✅                           | ❌ **必须排除**（见 §4.2 ④） |
| 必须填操作人              | ✅                           | 建议填，不强制              |
| 能做几次                | **可补录 / 可重做**（不永久封锁，见 §6.1） | 可多次（幂等去重）            |
| 在流水里的标记             | `origin='opening'`          | `origin='import'`    |

### 6.4 第一期的范围（按决策 2 修正）

⚠️ 初稿写的是"第一期允许暂不维护库存"，**与你决策 2 明确相反，此处已改**。

**决策 2 的要求：必须维护库存数量，但不建设复杂仓储管理。**

| 能力                            | 第一期                   | 说明                               |
| ----------------------------- | --------------------- | -------------------------------- |
| 品类                            | ✅ 必须                  |                                  |
| **库存（`holder_kind='stock'`）** | ✅ **必须维护**            | 按品类 + 归属对象 + 数量管理；库存可带存放位置（§2.4） |
| 入库                            | ✅ 必须                  | 备件进来登记一次                         |
| 分配 / 装到资产 / 放到点位              | ✅ 必须                  |                                  |
| 归还 / 转移 / 报损                  | ✅ 必须                  |                                  |
| **盘点调整（盘盈 / 盘亏）**             | ✅ **必须有**，且**留审计**    | 数量不对时的正规修正通道                     |
| 期初盘点                          | ✅ 建立上线基准              | 但**不永久封锁**，允许后续补录与调整             |
| 流转历史                          | ✅ 必须                  |                                  |
| 资产详情 / 点位详情里看配件               | ✅ 必须                  |                                  |
| 采购订单 / 供应商 / 批次 / 成本核算        | ❌ **不做**（项目边界，且非真实需求） |                                  |

**"维护库存"与"不做仓储管理"的界限**（避免实施时滑向任何一边）：

- **要做的**：库存数量准、能看到备件放在哪（`stock_location`）、数量不足时拒绝扣减、

  盘点能修正且留痕。这四件事构成"库存可用"的底线；
- **不做的**：不给库房建货位编码体系、不出入库单据、不做调拨审批、不记采购价与批次。

  它们不是"以后再说"，而是**本项目约束里明确排除的边界**（不碰采购/合同/财务/审批流）。

数量不足时的行为（决策 2 明确）：**禁止扣减** —— 这是硬校验，409 + 人话，

不允许"先记成负数以后再补"。

## 7. 正式资产报废时怎么提示（对应问题 4）

### 7.1 场景

`A100-03-00001` 要报废，上面还插着 2 条内存、装着 1 块 SSD。

如果直接报废，这些配件在账上会挂在一台"已报废"的机器上 —— 数字对，但没人会去查，等于失踪。

### 7.2 方案：在报废动作里前置提示，绝不自动改配件归属

现有 `run_operation`（`backend/app/routers/assets.py:507`）已经有完整的状态机校验。

本方案**不改变它的状态机**，只在 `SCRAP` 动作前增加一次关联检查，复用项目已有的

**"预检 → 确认 → 执行"** 范式（`relocation.py` 的 `confirmations` 机制，

前端 `payload.acknowledge_warnings` 点头才继续 —— 这套东西项目里已经跑通了，直接借用形状）。

流程：

1. 用户对资产点"报废" → 后端检查 `light_holdings WHERE asset_id=该资产 AND quantity>0`；
2. 有配件 → **返回 409（或带 `confirmations` 的预览）**，明确列出：
   > 这台设备上还登记着：金士顿 DDR4 8G × 2 条、宏碁 N3500 256G × 1 块。
   >
   > 请先决定这些配件怎么处理：拆下来回库存 / 转到别的机器上 / 随设备一起报废。
3. 用户选择处理方式 → 执行对应的轻资产动作 → 再真正报废设备；
4. 或者用户明确选"随设备一起报废" → 同时把配件的持有记录报损，**在同一次确认里说清楚**。

### 7.3 为什么"绝不自动改归属"

这是全站一致的原则（红线：不做隐式联动）。自动把配件改成"库存"或"跟着人去"，

会凭空造出一个**没有人做过**的业务决定 —— 而现实里配件可能是拆下来、可能是随机器一起扔、

也可能转到别的机器，只有人知道是哪种。

### 7.4 另一个可选入口：问题中心规则

项目已有问题中心（`services/issues.py`，`RULES` 里加一条 = 一个常量 + 一条规格 + 一段判定）。

可以加一条规则：

> `ASSET_SCRAPPED_WITH_LIGHT_ASSETS`：状态为"已报废"的资产上仍挂着轻资产 → 进问题中心待办。

**价值**：报废那一刻用户可能点了"随设备一起处理"却改主意，或者历史遗留数据本来就有这种情况。

问题中心能把"漏掉的"兜住，而不是只在报废那一瞬间提示一次就过了。

**建议**：§7.2 的报废前置提示**要做**（成本低、那一刻最关键）；

§7.4 的问题中心规则**可后置**（第二期，属于兜底，不是主路径）。

## 8. 数据库最少需要新增哪些表与字段（对应问题 7）

### 8.1 结论：**新增 1 张表、改 1 张表、删 1 张表 = 净减**（决策 6）

| 动作        | 对象                 | 说明                                           |
| --------- | ------------------ | -------------------------------------------- |
| **新增**    | `light_holdings`   | §2.1 的结构。承载"当前分配记录"                          |
| **保留并简化** | `light_movements`  | 表本身保留（上一轮已建），字段沿用；**流水里 `item_id` 相关引用全部作废** |
| **删除**    | `light_items`      | 单件档案表，整个删掉（见 §8.3）                           |
| **改**     | `light_categories` | **删 `tracking` 列**（双模式的开关）                   |

**删表前核查（决策 6 明确要求）**：删除 `light_items` 之前必须

① 核查旧表数据（逐条判定，见 §8.3）；② 核查依赖关系（`light_movements.item_id` 是唯一引用方，

无其他表引用）；③ 核查迁移影响（迁移报告里的数量与归属差异先人工核对）。

**不误删有效业务数据** —— 判定为"有实际业务意义"的旧档案全部转成持有记录后才删表。

**同步废弃的清单（决策 6）**：

- 后端：`models.LightItem`、`schemas_light.LightItem*` DTO、`routers/light.py` 的单件接口、

  `services/light.py` 的单件派生函数、`services/light_serialize.py` 的单件序列化；
- 前端：`LightItemDialog.vue`、`LightItemDetailDialog.vue`（上一轮新增，随单件作废）、

  `LightCategoryView.vue` 的"单件清单"页签、`types.ts` 的 `LightItem*`、

  `api/index.ts` 的单件方法与 `itemHistory`；
- 测试：`test_light.py` 里单件相关的用例（保留其余）。

**第一阶段不保留单件追踪模式、不维护轻资产 SN**（决策 6）。

以后真有新的业务需求，再设计对应能力 —— 不为假设中的需求付维护成本。

> **注意表数量是净减的**：第一版 3 张表（categories / items / movements），
>
> 本版 2 张表（categories / movements）+ 1 张新表（holdings），净增 0 张、净减 1 张。
>
> 这是"取消双模式"直接带来的简化。

### 8.2 `light_categories` 的改动

```
- tracking   VARCHAR(16) NOT NULL   -- 删除：不再有数量/单件之分
```

其余保持：`name`(UNIQUE) / `brand` / `spec` / `unit` / `notes` / `active` / 时间戳。

**为什么 unit 保留**：它是"套 / 条 / 块 / 个"的展示单位，与人读数字直接相关，不是抽象层。

### 8.3 `light_items` 的处置（按决策 3 定稿）

按你的约束，不再有单件身份，`light_items` 整表删除。但**旧数据怎么转，判定依据必须说清楚**。

⚠️ **初稿这里写错了，已改**：初稿说"有过流转的转成持有记录"，这是错的 ——

**"有过流转"不等于"现在是持有"**。举例：一件 SSD 曾经入库、后来报损了，

它有流转记录，但最终状态是"已退出管理"，转成持有量就会**凭空造出一件在库的东西**。

所以判定依据必须是**按最终状态**，不是"有没有历史"。

**迁移判定表（每一条 `light_items` 记录走一次）**：

| 该单件的最终状态     | 怎么判                                                        | 迁移动作                  |
| ------------ | ---------------------------------------------------------- | --------------------- |
| **在库**       | 重放其有效流水（`manual`/`opening`，排除 `import`）后 `to_kind='stock'` | 对应品类的库存 **+1**        |
| **在某资产上**    | 最终 `to_kind='asset'`                                       | 该资产持有 **+1**          |
| **在某点位上**    | 最终 `to_kind='workstation'`                                 | 该点位持有 **+1**          |
| **在某使用人手上**  | 最终 `to_kind='user'`                                        | 该使用人持有 **+1**         |
| **已报损 / 注销** | 最终 `to_kind IS NULL`，或 `active=False`                      | **不生成任何持有记录**（它已经退出了） |
| **从未流转过**    | 没有任何有效流水（如真实库里那条 `id=1, cat=2, active=1`）                  | **不生成持有记录**，进"待清理"清单  |

**同一个品类多条单件合并**：逐条按上表得出"落在同一个位置"，然后**按位置聚合求和**

（3 件都装在 A100 上 → 一条 `quantity=3` 的记录），不是生成 3 条。

**两条硬性要求（决策 3）**：

1. **不得把所有有流转记录的旧档案一律转成当前持有数量** —— 必须逐条看最终状态（上表）。
2. **空档案可以清理，但禁止静默删除** —— 脚本把"从未流转 / 已报损"的档案**列进清理清单**，

   报告里逐条打印（id、品类、序列号、判定理由），确认后才删。

**迁移前检查项（决策 3 要求"检查关联、引用和最终状态"）**：

- 每条单件的 `category_id` 是否仍指向存在的品类（否则归到"异常"清单，不猜）；
- 其最终状态指向的 `asset_id` / `workstation_id` 是否**仍然存在**（宿主已删的，

  按 §5.2 的编码快照回落，标为"宿主已删除，需人工确认归属"，**不自动丢进库存**）；
- 是否与已有流水矛盾（如流水最终状态算出"在库"，但 `active=False`）→ 列进异常清单等人工判。

**执行方式（决策 3 + 实施约束）**：

- **先备份**（复用 `backend/backup_db.py`，含完整性校验）；
- **默认干跑**，输出迁移报告：逐条判定结果 + 每品类"迁移前 → 迁移后"的持有量对比
  - 清理清单 + 异常清单；
- **核对数量及归属差异之后**才 `--apply --confirm` 正式执行（与 §4.2 ③ 的重建同一套确认纪律）；
- 全程在**临时库**上先跑通，再对真实库执行（实施约束要求）。

**真实库里那条已知记录**：`id=1, category_id=2, serial_number=NULL, label=NULL, active=1`，

经只读核对**从未有过任何流水**（`light_movements` 里 `item_id=1` 计 0 条）。

按上表属"从未流转过"→ **不生成持有记录**，进清理清单。决策 3 要求"迁移时再次核实后处理" ——

脚本会重新查一次它的流水与关联，不依赖此刻的结论（因为期间可能有人动过它）。

**流水里指向单件的引用**：`light_movements.item_id` 不再有意义。

**保留列但不读不写**（SQLite 物理删列要重建表，收益小于风险）；新写入的流水 `item_id` 恒为 NULL，

序列化层不再输出它。

> ⚠️ 迁移脚本必须**先备份库**（复用 `backend/backup_db.py`，项目已有在线备份 + 完整性校验），
>
> 且默认**干跑**（打印将要发生什么），`--yes` 才写 —— 与项目里 `link_workstations.py`、
>
> `restore_station.py` 这些脚本同一套约定。

### 8.4 复用 `BUSINESS_TABLES` 的记账机制

`database.py::BUSINESS_TABLES` 需同步（红线 7：新增/删除表必须登记，`reset.py` 会按它清库，

删除顺序要按外键依赖排 —— 先删引用方）：

```
..., light_movements, light_holdings, light_categories, assets, relation_exceptions,
workstations, floor_maps, audit_logs
```

`light_holdings` 引用 `light_categories` + `assets` + `workstations`，所以要排在这三者**之前**删除。

老库迁移：`create_all` 会自动建新表（零迁移代码）；

`light_categories` 删列与 `light_items` 删表**需要一次性迁移脚本**（老库的 `ALTER TABLE DROP COLUMN`）。

## 10. 每项设计解决的实际业务问题（对照你的要求）

| 设计                      | 解决的真实问题                                       | 不做会怎样                              |
| ----------------------- | --------------------------------------------- | ---------------------------------- |
| 删掉 `tracking` 双模式       | 用户不必先回答一个自己都不知道的问题（"这东西要不要逐件追？"）；SSD 也能像键鼠一样管 | 界面继续问一个多余问题，两套逻辑长期并行               |
| `light_holdings` 落库当前状态 | 列表页打开是快的；"现在这台机器上有什么"一条索引查询解决                 | 每次列表都要重放全部历史（第一版的性能与复杂度问题）         |
| 一记录一位置（四选一）             | 不会出现"张三 AND W23"这种无法回答的状态；也回答了"人调岗，配件跟不跟走"    | 归属含糊，盘点时无法判断该去哪找                   |
| 使用人只现读、不推断点位            | 避免"因为张三名下有 W23，就把他的键鼠算在 W23"这种凭空推断            | 一个多工位的人，配件位置全算错                    |
| 流水 + holdings 双写        | 既有快照的简单，又有历史的完整；坏了能重建                         | 纯派生太慢、纯快照丢失过程                      |
| 编码快照（不只存 id）            | 资产/点位删除后，历史依然指得准（本库 id 会复用）                   | 删一台设备再建一台，旧历史挂到新设备上                |
| 期初 vs 导入分离              | 不会把 Excel 里的历史分配当成"现在的账"                      | 负库存或凭空多出的持有量                       |
| **期初不永久封锁**（决策 2）       | 上线后漏录品类、或盘点发现数量不对时，仍能通过有记录的调整纠正               | 否则 `schema_meta` 一标记完成，用户只能想办法绕过系统 |

## 11. 接口清单（实施时用）

## 14. 本方案自身的风险与未决问题（对抗性自查）

1. **双写的一致性依赖纪律（已由决策 1 接受）**。所有写路径必须走 `apply_holding_delta()`，

   没有数据库层强制。按决策 1：单一入口 + 同事务双写 + 只检查不修复的体检 + 先报告后重建。

   **明确禁止**以"有体检和重建"为由放宽事务要求。
2. **`quantity` 与单位的关系没约束**。"3 套键鼠"和"3 个转接头"单位不同，

   系统不阻止把单位从"套"改成"个"（改单位不回算历史）。建议：单位仅作展示，允许改，不做校验。
3. **部分归还没有"批次"概念**。张三拿了 3 套、还了 1 套，系统只知道"张三还有 2 套"，

   不知道还的是哪一套（其实也不需要 —— 同一品类的套件本来就不可区分）。

   若将来需要区分（如不同批次采购价不同），要另加批次维度。**现在不做**。
4. **使用人降级为展示信息后，"发给某人"的配件查不到位置**。这是决策 4 明确要的取舍

   （人不推断点位）。系统**不会**告诉用户"张三名下那套键鼠大概在哪"；

   若需要位置，只能改记为一个点位持有记录。
5. **点位删除与资产报废的处理是"拦住 + 提示"，不是"自动处理"**（决策 5）。

   如果用户习惯性点"确认"，仍可能在没有真正处理配件的情况下继续 ——

   缓解：直接关联的配件是 **409 硬拦截**（不是可关掉的警告），必须先处理归属。
6. **地图图层（§5.5）暂不做**。如果"看一眼这张图就知道哪些工位有配件"是硬需求，

   需要提前说，它会改变 §5 的工作量。
7. **老库迁移不可逆**（删 `tracking`、删 `light_items`）。迁移脚本会先备份，

   但备份恢复需人工操作。真实库目前只有 2 个品类 / 1 条空单件档案，风险极低；

   迁移前仍必须先跑干跑、核对报告。
8. **`light_holdings` 不存"最近一次变动时间"之外的历史**。"这个位置从什么时候开始有这些件"

   能答（`since`），"这个位置上有过几批"要看流水 —— 设计如此，不是遗漏。
9. **`stock_location` 是自由文本，不做规范性校验**（决策 4 的取舍产物）。

   好处是能写"3 楼库房A柜"，代价是同一个库房可能被写成几种名字，

   库存按存放位置分组的统计会出现"库房A"和"库房 A"两条。

   缓解：界面提供已有值的候选（复用 `composables/useFreeTextOptions.ts` 的拼音+新建项垫底范式），

   但不强制。**建议第一期接受这个不完美，等真有多个库房时再考虑规范化。**
10. **体检脚本只能发现"表 vs 流水"的不一致，发现不了"两处都错"的情况**。

    例如一次错误操作同时写坏了 holdings 和流水（概率低但非零），

    体检会认为两者一致。缓解：关键校验放在写入路径上（守恒断言 + 数量非负 + 唯一约束），

    让"两处都错"在写入那一刻就被拦住，而不是靠事后体检。

## 0. 一句话结论

你的判断是对的，而且比"功能不全"更严重：**现在轻资产的核心写入口存在数据正确性缺陷 —— 能凭空造出库存、能让台账自相矛盾、能让人点一个必然报错的按钮。**

这不是"没做完"，是**做错了**。而且错的这一处（数量模式的持有量校验）会让整套"流水派生当前状态"的设计前提失效：派生逻辑本身是对的，但喂给它的流水可以是假的。

## 1. 严重缺陷：账面能凭空多出东西

### 1.1 【严重】数量模式从不校验"持有方手上真有这么多"

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/app/services/light.py:458` `_check_stock_enough()` |
| 根因 | 只在 `from_kind == 'stock'` 时校验库存够不够。**从人 / 资产 / 点位发出的操作完全不校验**。 |
| 影响面 | `allocate` 之外的**全部**从持有方出发的操作：`return`、`transfer`、`scrap`、`detach` |

**实测复现（接口层，真实 HTTP 200，不需要改代码或写库）：**

```
入库 3 套                 → 库存 3，已分配 0
分给「李四」3 套           → 库存 0，已分配 3      持有明细=[李四×3]
从「王五」归还 3 套（他从未拿过任何东西）
                          → HTTP 200 写库成功
  结果：库存 3，已分配 0，持有明细=[李四×3]      ← 同一屏自相矛盾
再发 3 套给「赵六」        → 库存 0，持有明细=[李四×3, 赵六×3]
```

**真实入库只有 3 套，台账上却发出了 6 套。**

这条为什么隐蔽：`category_holders()` 结尾用 `row.quantity > 0` 过滤（`services/light.py:312`），把"李四 −3 + 王五 +3"这种负数持有行**静默丢弃**了。于是页面不会显示负数，看起来"很正常"，只有把卡片数字和持有明细并排读才会发现矛盾 —— 而页面恰好把它们放在同一屏。

**同类：从持有方报损 999 个也能写进去。** 从「孙七」（从未持有一件）报损 999 个 → 写库成功。

### 1.2 【中】"自己人之间换手"没有正确路径

`LightOp.FLOWS` 里 `transfer` 允许 6 种组合，**没有 `user → user`**。也**没有"修改持有人"这个操作**。

于是"这 2 套本来在张三名下，现在改归李四"只能走 `归还 + 分配` 两步 —— 而"归还"的持有人是自由填写的，正好踩中 1.1 那个洞。**正确业务意图只能用有缺陷的路径完成。**

## 2. 严重缺陷：界面上的死按钮

### 2.1 【中】「冲正」按钮对 6 种流水点下去必然报错

| 项 | 内容 |
| --- | --- |
| 前端 | `frontend/src/views/LightCategoryView.vue:434-443`，只写了 `:disabled="row.origin === 'import'"` |
| 后端 | `backend/app/models.py:1164` `REVERSE_CANDIDATES`，`scrap` 的反向候选是**空元组** |

实测：把一块 SSD「安装」到主机上 → 点该条流水的「冲正」→ **HTTP 400**
`「安装」不能机械冲正 —— 它的反向没有定义……请用对应的操作来更正。`

**共 6 种可写组合点冲正必然失败**：

| 操作 | from → to | 反向 |
| --- | --- | --- |
| 安装 | 系统外部 → 正式资产 | 无 |
| 安装 | 系统外部 → 点位 | 无 |
| 报损 | 库存 → 系统外部 | 无 |
| 报损 | 使用人 → 系统外部 | 无 |
| 报损 | 正式资产 → 系统外部 | 无 |
| 报损 | 点位 → 系统外部 | 无 |

后端的设计判断（"报损想撤销必须由人决定走哪条路，系统不替你做判断"）**是合理的**；错的是前端照旧渲染了一个点了就报错的按钮。要么按 `reverse_op()` 的结果决定是否显示，要么把这些行改成引导到正确操作。

### 2.2 【中】已报损的件能被静默复活

报损后单件状态 `gone=True`（"已报损/注销"），但再走一次「入库」就能让它变回"在库"，且该品类「已报损」计数**立刻归零**。

报损语义是"彻底退出管理"，却能无声撤销。这与 `active=False`（注销）构成两套互不衔接的退出机制。

## 3. 界面：与"系统原本的气质"确实不符

我对比截了同一系统两个页面（`.tmp/qa-asset-list.png` vs `.tmp/qa-light-list.png`），差异是结构性的，不是配色问题。

| 维度 | 资产台账（成熟页） | 轻资产（现状） |
| --- | --- | --- |
| 列表形态 | 4 列**卡片网格**，字段图标化 | 裸 `el-table` 密集表格 |
| 统计卡 | 5 张，**带线性图标 + 语义配色**（在用绿 / 库存橙 / 无点位红），首张可点当筛选器 | 4 张，**无图标、无语义配色**，`label + 数字`（`LightListView.vue:114`） |
| 页面饱满度 | 24 张卡铺满整屏 | 2 行数据 + 分页后**下方约 45% 全空** |
| 图标体系 | 全站线性图标 | 详情页统计卡用 emoji `📦👤📋🗑️∑`，其中"净存在"配了个语义不搭的符号 |

**具体排版事故（已放大原图核实，非目测）：**

1. **「追踪」列文字被省略号截断** —— 列宽写死 `86px`（`LightListView.vue:213`），放不下"数量管理"/"单件管理"。同列两个取值还用了两种颜色（灰 vs 橙）却无任何图例。
2. **「操作」列三个链接挤到换行** —— `width="150"`（`LightListView.vue:252`），"详情 编辑"一行、"停用"折到第二行。
3. **术语自相矛盾** —— 品类详情页同时显示「库存 3 件」和「净存在 3 件」两张卡，数值相同、无任何解释。用户无法理解为什么要看两个一样的数字。

**这里直接踩了项目自己的硬约束。** `CURRENT_STATE.md:41` 原文：

> 中文界面，风格现代简洁，参考飞书/Notion，**不要传统后台那种密集表格感**。

轻资产页是**目前全站唯一一个纯密集表格列表页**。

## 4. 易用性：为什么"一头雾水"

### 4.1 唯一的写入口是技术模型，不是业务动作

`LightMovementDialog.vue` 是**唯一**的写入口，第一屏三个必填项是：

> 操作 / **从哪来** / **到哪去**

用户脑子里想的是"这套键鼠发给李四"，界面上要他选的是 `from_kind = stock`、`to_kind = user`。**中间那层翻译完全由用户自己完成。** 对 IT 管理员来说这不叫易用，这叫要他理解实现。

### 4.2 空态只解释、不给出路（且与列表页不一致）

品类详情页「持有明细」空态（`LightCategoryView.vue:298`）：

> 当前没有任何持有关系 —— 可能都在库存里，或者还没做期初初始化

**读完不知道点哪里。** 而列表页空态是有按钮的（"新增第一个品类"）。同一模块两处风格不统一。

### 4.3 自造术语无处解释

「未登记入库」「待期初初始化」「期初初始化」「净存在」「宿主当前使用人」—— 全站没有任何 tooltip / 帮助链接解释它们。

### 4.4 README 写得很清楚，但应用里没有入口

`README.md:466-540` 有一整节「轻资产怎么用」，写得确实好。**但应用内没有任何地方指向它** —— 用户必须先知道要去翻 README，才知道这套东西该怎么用。

## 5. 根因：它现在是个"外挂"，不是系统的一部分

这是"气质不符"最深的来源，也是比界面问题更该先解决的事。

轻资产模块与既有功能**零集成**：

| 应有的联动 | 现状 | 实测 |
| --- | --- | --- |
| 资产详情页显示"这台机器上挂了什么配件" | **完全没有** | `AssetDetailView.vue` 中 `light`/`配件` 命中 **0** |
| 点位面板显示点位上的配件 | **完全没有** | `MapStationPanel.vue` 命中 **0** |
| 问题中心纳入轻资产规则 | **完全没有** | `InsightsView.vue` 命中 **0** |
| 批量导入页支持轻资产流水 | **完全没有** | `ImportView.vue` 命中 **0** |

后果：**查看一台主机时，看不到它身上装了什么 SSD。** 而这正是 `设计方案-轻资产管理模块.md` 第 2.11 节验收场景 3、6、7 的核心诉求。

设计文档把这些放在 P1（见 2.8 表 `/by-asset` `/by-workstation` 标注 P1），所以**代码是照文档做的、但文档本身把用户感知最强的联动排到了后面**。这解释了为什么"做完了却和系统气质不符"。

## 7. 修复建议（按优先级）

### P0 —— 修正确性（不修则整个模块不可信）

1. **补"持有方余额"校验**：数量模式下，任何 `from_kind ∈ {user, asset, workstation}` 的操作，先算该持有方当前持有量，不足则 409 + 人话。落点在 `_check_stock_enough()` 旁边，注意 `transfer` 的 `from` 侧同样要查。
2. **把守恒变成断言**：`category_holders` 里 `quantity > 0` 的静默过滤，改成"出现负数则报错/记日志"，别再让矛盾被藏起来。
3. **补 `user → user` 转移**（或新增"改持有人"操作），让正确业务意图有干净路径。
4. **冲正按钮按后端能力渲染**：前端用 `reverse_op()` 的结果决定显示/禁用，或把无反向的操作引导到正确动作。
5. **报损不可静默复活**：`stock_in` 对 `gone=True` 的单件应 409，要求走"撤销报损"这类显式动作。

### P1 —— 让界面回到系统水准

6. 列表页从裸表格改成与资产台账一致的**卡片网格**；统计卡补图标 + 语义配色。
7. 修掉 `86px` 截断、`150px` 换行、以及「库存 / 净存在」重复卡。
8. emoji 图标换成全站线性图标。
9. 登记流转弹窗改为**按业务动作组织**（"发给某人" / "装到某台机器" / "收回库存" / "报损"），把 from→to 藏到实现层。
10. 空态补出口按钮；给自造术语加 tooltip；应用内加指向 README 那节的入口。

### P2 —— 补上真正让它是"系统一部分"的联动

11. 资产详情页 + 点位面板加"关联配件"区块（`/by-asset`、`/by-workstation`）。
12. 批量导入页加轻资产 Tab（`/import/preview` + `/import`）。
13. 主机报废时的配件确认（场景 7）+ 问题中心规则。
14. 统一设计文档与 CHANGELOG 对 P0/P1 的口径。

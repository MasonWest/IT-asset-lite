## 0. 结论摘要（先看这一页）

1. **体量不是均匀分布的，问题集中在一个东西上**：`CURRENT_STATE.md` 187 KB 里，**第七节「关键设计决策」独占 78.6 KB（42.7%）**，全部是 104 条"一条一行"的巨型表格行（合计 37,677 字符，平均 362 字符/条，最长 873 字符）。其余 13 节加起来 105 KB。
2. **REAME 长不是"写得啰嗦"，是它已经是用户手册**：739 行 / 55 KB 里有 8 个完整业务章节（地图 8.0 KB、日常操作 12 KB、轻资产 5.5 KB…），同时塞了 4 段开发/运维内容（手动构建、环境变量表、维护命令×2）约 9.5 KB（17%）。**两件事的方向相反**：README 混进了开发内容，CS 混进了历史与实现细节。
3. **最大风险不是"太长"，是 12 处事实性自相矛盾**（第 2.2 节 F1–F12），其中 3 处会被后来者直接当成事实用错：
   - CS 说"九张表"，`models.py` 实际 **13 张**（第 128、260 行）；
   - CS 说"真实库 142 台资产 / 89 台有点位 / 62 个点位"，**实测库现在是 150 / 126 / 69**；
   - CS 页脚写"最后更新 2026-10-12 · 基线 v2.4.1"，头部写 v2.9.10（差 9 个版本）。
4. **15 份文档是孤儿**：全仓库只有 `README ↔ CURRENT_STATE ↔ CHANGELOG` 三者互链，其余 13 份**没有任何入链**（只有 2 份被 CHANGELOG/CS 顺带提到）。同时 **5 份设计稿根本不在 Git 里**（未跟踪、未忽略）—— 这是"唯一设计决策记录"最容易丢的一类。
5. **没有任何文档发布机制**：无 `.github/`、0 个 workflow、Pages 返回 404、无 mkdocs/docusaurus/vitepress 配置。这是一张白纸，**先定结构比先选工具重要**。
6. **建议**：结构先做「A 方案（纯 Markdown + 目录分层）」，VitePress + Pages 作为最后可选加装（Phase 6）。理由与触发条件见第 5 节 —— 先说结论：**VitePress 解决的是"怎么读"，你现在的问题是"读到的东西是错的、散在根目录、没入版本库"。**
7. **一个必须先处理的隐私问题（且它是一次"回归"，不是遗留）**：v2.0.0 曾专门做过匿名化（CHANGELOG L2393：「真实姓名全部匿名化」「真实资产编号全部替换为合成编号 → `A100-01-xxxxx`」）。但 **v2.9.x 之后的新文档又拿真库举例了**：CS 第 1077 行写「播一条"**员工A**持有键鼠"（他名下有 **W52、W63** 两个点位）」，而真库里 **`员工A` 恰好有 6 台设备 + 正好 W52/W63 两个点位** —— 姓名与点位都能对上，这是真实信息；真库资产编号 `A100-03-xxxxx` 也在 6 份文档里出现 29 次（合成编号 `A100-01-` 仍在另 6 份里用，两套并存）。同时 `林晓薇 / 陈思远 / 林晓威` 经查**库内 0 命中**，属 v2.0.0 留下的虚构占位符 —— **两类不能混为一谈**。仓库公开 + 刚加 Apache-2.0，上 Pages 会把这些变成可被索引的页面。**本报告不擅自改，列为决策项 6。**

### 2.3 隐私：一次**匿名化回归**（不是"从没做过"）

> 这一节初稿写成"文档里有真实员工姓名"，取证明时**推翻了一半**。下面是核对后的结论 —— 两类别混着说，会导致"把虚构占位符也当成泄漏去改"，反而制造新的不一致。

**背景**：CHANGELOG L2393（v2.0.0 公开前）明确记过两条动作：真实姓名全部匿名化、真实资产编号全部替换为合成编号（`A100-01-xxxxx`）。

**核对方法与结果**（真库 `?mode=ro` 只读查询）：

| 待查项 | 库内核对 | 结论 |
| --- | --- | --- |
| `林晓薇` | assets 0 / workstations 0 | **虚构占位符**（v2.0.0 遗留，符合记录） |
| `陈思远` | assets 0 / workstations 0 | 虚构 |
| `林晓威` | assets 0 / workstations 0 | 虚构（"手打成林晓威"这个举例本身就要求库里没有） |
| **`员工A`** | **assets 6 / workstations 2（正好 `W52`、`W63`）** | **真实** |
| 资产编号 `A100-03-xxxxx` | 真库实际编号格式就是 `A100-03-xxxxx`（如 `A100-03-00035`） | **真实** |

**最直接的一处**：CS L1077 的验收脚本说明写着「额外播一条"**员工A**持有键鼠"（**他名下有 W52、W63 两个点位**，否则歧义分支覆盖不到）」—— 姓名、两个点位号、"名下持有"这三件事与真库**逐项吻合**，不是巧合。这行是 v2.9.6 新增的，属**匿名化之后的新回归**。

**分布**（`grep -c`）：

| 项 | 命中 | 文件 |
| --- | --- | --- |
| `员工A` | 7 | CS 4（L403/L410/L623/L1077）、CHANGELOG 2、`设计方案-空间地图搜索拓展.md` 1 |
| `A100-`（真编号格式） | 29 | CHANGELOG 10、`修订版` 10、CS 3、旧稿 3、`交付说明` 2、`搜索拓展` 1 |
| `A100-01-`（合成编号） | 21 | `自动配对提示` 11、`第一阶段开发规格与验收` 5、CHANGELOG 2、CS 2、README 1、`Phase3` 1 |

→ 附带一个**一致性问题**：同一份仓库里两套编号风格并存，读者无法判断哪个是"真编号"。这比隐私本身更容易造成误读（有人会拿 `A100-03-00043` 去库里搜，发现"查得到"就以为文档是准的）。

**判断**：仓库 `private: false`（公开）+ 刚加 Apache-2.0，**现有 md 的真实项已经公开**；`.gitignore` 只能挡未来。**上 Pages 会把它们从"仓库里能翻到"升级为"搜索引擎可索引"** —— 这是第 5 节把它列为 Phase 6 硬前置的原因。

**本报告只标记、不修改**（见决策项 6）。若要连历史 commit 一起清，需要 `filter-repo` 改写历史，影响所有 clone/fork —— **不建议**（CHANGELOG 自己也记过同样的取舍：「用新提交盖过去，不洗历史」）。

## 5. 文档网站方案比较：A（纯 Markdown）vs B（VitePress + GitHub Pages）

### 5.1 逐维度对比

| 维度 | **A. 纯 Markdown + 相对路径链接** | **B. VitePress + GitHub Pages** |
| --- | --- | --- |
| **实施成本** | 接近 0：只建目录、搬文件、写 `docs/README.md` 索引。（本次审计本身已经完成了 80% 的设计工作） | 中：`docs/package.json` + `.vitepress/config.mts`（导航/侧边栏/搜索）+ 首次 `npm install`（引入第 2 套 Node 工具链，本仓库已有 1 套）+ 一个 workflow 文件。工作量估计半天到 1 天，但**返工点在于"目录结构定稿前就配侧边栏"** |
| **日常维护成本** | 低：加一篇 md 就在索引里加一行；无构建、无依赖升级 | 中：每加一篇要进 sidebar（可用 glob 自动生成缓解）；VitePress 大版本升级要跟着改配置；**CI 红了要有人看**（本项目目前 0 workflow，等于新增一个"要维护的流水线"） |
| **导航** | 弱：靠 `docs/README.md` 的目录表 + 编辑器/GitHub 的文件树 | 强：左侧分组导航、上一页/下一页、面包屑、页内目录（TOC） |
| **搜索** | 无（只有 GitHub 仓库搜索和 Ctrl+F） | **强**：内置本地全文搜索（构建时生成索引，无需后端服务）；中文分词效果一般但够用 |
| **移动端阅读** | 一般（GitHub 网页版可读） | 好（响应式 + 暗色主题） |
| **部署权限** | 不需要任何权限 | 需要仓库 **Settings → Pages**（admin 权限）+ workflow 的 `pages:write` / `id-token:write`。**首次配置必须由仓库 owner 手动点一次** |
| **私有仓库限制** | 无限制：有仓库读权限就能看 | **private 仓库的 Pages 需要 GitHub Pro/Team/Enterprise**，且默认可访问范围受限。**本仓库当前是 public → 免费可用**；但如果将来转 private，**站点会失效**（这是一条容易被忽略的耦合） |
| **公开性副作用** | 文档在 GitHub 页面可见（已被搜索引擎收录的是仓库页） | **文档变成独立站点，可被搜索引擎索引、可被任何人分享链接** → 与 2.3 的真实姓名问题直接冲突 |
| **未来迁移成本** | A→B 很低（VitePress 直接吃标准 md，把 `docs/` 指过去即可） | B→A 也低（md 还在原地），**前提是没大量使用 VitePress 独有语法**（`::: tip` 容器、`<script setup>` 交互块） |
| **对"agent 可读性"的影响** | **最好**：agent 只读需要的文件，路径稳定 | 稍差：多一层"站点 ↔ 源文件"的映射（源码仍在 `docs/`，其实不受影响） |
| **对本项目特有的风险** | 无新增 | ① 新增 Node 工具链（本仓库刻意"不建 venv、不装第二个运行时"）；② 新增 CI（当前 0 workflow）；③ 公开站点化 → 隐私放大 |

### 5.2 结论与建议

**建议：先做 A，B 作为 Phase 6 的可选加装。**

三条理由（按重要性排序）：

1. **痛点不在"怎么读"，在"读的是错的 / 找不到 / 没入库"**。F1–F12 这 12 条矛盾、13 份孤儿、5 份未入库文档 —— VitePress 一条都解决不了；反过来，结构理顺之后，加 VitePress 是"装个壳"。**先装壳等于把错误内容包装得更漂亮。**
2. **A 是 B 的严格前置**。VitePress 的侧边栏本质是"目录结构的可视化"，目录没定稿就配侧边栏 = 必然返工。等 `docs/` 稳定（Phase 5 结束）再上，配置可以一次写对。
3. **本项目的运行哲学是"零额外工具链"**（不建 venv、不装依赖、双击 bat 就起）。B 会引入第二套 Node 工具链 + 一条 CI 流水线，**与现有约定冲突**，应当由你明确批准，而不是顺手引入。

**触发 B 的条件（满足任意两条再启动）**：
- `docs/` 页面数 ≥ 15（现在拆完预计 25+，所以这条会很快满足）；
- 需要给**非 GitHub 用户**（客户、不熟的同事）看手册；
- 需要在手册里**搜关键词**（比如"二维码扫不出来"）；
- 想让用户手册能打印 / 有侧边栏导航。

**如果决定直接上 B**（不做 A 阶段），也成立，但必须同时接受：先定稿目录再配导航、先脱敏再发布。最小配置清单（**本阶段不安装、不创建，仅列出**）：
```
docs/package.json          { "scripts": { "docs:dev": "vitepress dev", "docs:build": "vitepress build" }, "devDependencies": { "vitepress": "^1.x" } }
docs/.vitepress/config.mts  title / description / lang:'zh-CN' / themeConfig.sidebar（按 user、dev、design 三段）/ search: { provider: 'local' }
.github/workflows/docs.yml  permissions: { contents: read, pages: write, id-token: write }；build → upload-pages-artifact → deploy-pages
```
外加一件事：**Pages 的"Source"必须在仓库设置里手动切成 "GitHub Actions"**（这是一次性人工操作，权限要求 admin）。

# 空间地图 · 搜索框功能拓展设计方案

> 状态：已实施（v2.9.5）· 2026-10-19

> 落地记录：**v2.9.5（2026-10-19）**，commit `f44fead`｜实施时按用户拍板：五处收口 / 全域搜 /
> 资产只搜编号+品牌 / 「不在图上」给跳转 / 不自动居中 / 首次聚焦才拉索引。
> 与原稿的差异：期初方案 §6.2 里的「C. 显式范围胶囊」未做（二期可选）。
> 结论先行：**房间该去掉；资产编号与轻资产都该能搜；但「点开轻资产层才能搜轻资产」这个绑定不要做**——用全域搜索 + 结果面板分组替代。

---

## 0. 一句话结论

现在的搜索框只匹配「点位编码 / 点位使用人 / 点位房间」三个字段，**它连自己页面上看得见的东西都搜不到**：资产编号搜不到（资产数据只缓存了当前点开的那个点位），轻资产搜不到（点位数据只带件数、不带品类）。所以问题不是"能不能加上"，而是**搜索的证据链压根没接上**。

要加就一次加对：

1. 删 `room`（67/69 为空，且系统口径里没有"房间"这个维度）；
2. 补「资产编号 / 财务号 / SN / 品牌型号」→ 点亮资产所在的点位；
3. 补「轻资产品类 / 品牌 / 规格 / 库存位置」→ 点亮配件所在点位；
4. **把"搜到了但不在地图上"的那部分显式列出来**（人员持有的配件、未挂点位的资产）——这是这次设计里最容易漏、也最容易让人以为"搜索坏了"的一块；
5. 图层开关只决定"画不画角标"，**不参与"搜什么"**。

| 事实 | 数值 | 对设计的意义 |

| 轻资产品类 | 3 个（其中 1 个已停用） | 品类少，直接按名称匹配即可 |

## 3. 问题清单

**P0（功能缺口）**
1. 搜不到资产编号/SN —— 页面上明明画着 126 台设备。
2. 搜不到轻资产 —— 图层能画出「轻×N」，但搜"SSD"毫无反应。
3. 命中但不在图上的东西没有出口 —— 人持有的配件、无点位资产，只能显示"没找到"。

**P1（口径不一致）**
4. `room` 作为搜索维度，与"系统只有点位/资产/人员"的口径冲突；且 67/69 个点位是空值。
5. 只改搜索不改输入口 → 用户还能在「新增点位」「批量生成」里填一个**永远搜不到**的房间 → 假承诺（项目已记过同类坑）。

**P2（反馈不足）**
6. 命中没有数量、没有原因，也没有"跳到某个命中点位"的动作；命中在缩放后视野外时只能手动找。
7. 搜单个字符（如 `W`、`B`）时全图点亮，等于没有高亮，而用户没有任何提示"再打几个字"。

---

## 4. 设计目标 / 明确不做

**目标**
- 一个框，一次输入，覆盖 4 个维度：点位、人员、资产、轻资产。
- **命中必须可解释**：告诉用户"这块为什么亮"，以及"还有几条不在图上"。
- 命中之后能**跳过去**（复用 `centerOnStation` + `select`）。
- 任何新增 UI 不得改变工具条高度（C1/C2 不许破）。

**不做**
- 不做独立的全站搜索页 / 全局搜索框（那是另一个功能，别塞进地图）。
- 不做搜索历史、不做拼音首字母以外的分词、不引新依赖。
- 不做 SQLite FTS / 后端全文索引（69+150+11 的规模，内存过滤足够）。
- **不动底图里的 `room` 形状**（`kind: 'room'` 的会议室/机房矩形是视觉分区，与点位上的 `room` 字段是两回事，别一起删）。
- 不改轻资产写入口、不改 holdings 模型。

## 5. 搜索维度矩阵（改完后）

| 维度 | 匹配字段 | 命中后点亮 | 匹配方式 | 现状 |
|---|---|---|---|---|
| 点位 | `code` | 自己 | 子串（`w23`/`W2` 都命中） | ✅ |
| 人员 | `workstation.user_name` | 该点位 | `matchByPinyin`（全名 + 全拼 + 首字母） | ✅ |
| 资产 | `asset_code` / `finance_code` / `serial_number` / `brand` / `model` | 资产所在点位 | 子串 + 拼音（品牌型号可能中文） | ❌ 新增 |
| 轻资产 | 品类 `name` / `brand` / `spec` | 配件所在点位（`asset` 宿主 / `workstation` 直挂 / `stock_location` 恰为点位编码） | 子串（"ssd" 命中"…SSD"） | ❌ 新增 |
| 房间 | ~~`room`~~ | — | **移除** | 删 |
| 不落点位 | `user` 持有的配件、无点位资产 | **不点亮**，单列在结果面板 | 同上 | ❌ 新增 |

关于资产匹配字段：台账的 keyword 匹配 `编号/财务号/品牌/型号/SN/使用人/位置/备注`（`services/filters.py:67-80`）。地图**不跟备注与 `location` 文本**——那两处是自由文本，搜"3楼"会把半张图点亮，噪音大于价值。编号类字段优先，品牌型号次之。

## 6. 交互设计

### 6.1 为什么不做「点开轻资产层才能搜轻资产」

这个想法方向是对的（要能按轻资产维度找），但**载体选错了**。四条理由，都有具体场景：

1. **开关语义冲突**：`lightLayer` 现在的职责是"画不画「轻×N」角标"（`1742` 的 title 写得很明确：只是标注，不筛选）。让它同时决定"搜什么"，等于一个视觉开关改变查询语义——同一个词，开关前后结果不同。
2. **会造出"搜索坏了"的现场**：开着轻资产层搜「员工A」，如果范围被锁到轻资产，命中 0——但 W52 上坐的就是员工A（真实数据）。用户的结论只会是"搜索坏了"，不会想到"哦我开了个图层"。
3. **关掉图层结果消失**：用户为了看图干净关了图层，再搜 SSD 什么都没有——数据没丢，但看起来丢了。
4. **窄屏上这个开关是藏起来的**：900px 以下它不在工具条里，而在「更多」下拉（`1801`，因为留在工具条会把 390px 撑到 131px / 固定区 21.7%，C1/C2 失守）。也就是说手机上要"先点更多 → 开图层 → 再搜"，而且界面上没有任何地方写着"当前搜索范围 = 轻资产"。

**替代方案：全域搜索 + 结果面板分组。** 你要的"专门搜 SSD"由面板里的「轻资产 7」分组直接满足，还附带"为什么命中"。

### 6.2 方案对比

| | A. 全域搜索（推荐） | B. 绑图层 | C. 显式范围胶囊 |
|---|---|---|---|
| 可预测性 | 高：一个词一个结果 | **低**：隐藏状态 | 高：范围写在界面上 |
| 可发现性 | 高：不用教 | 低：没提示 | 中：要看一眼 |
| 窄屏成本 | 0（面板是浮层） | 0，但多两步操作 | 中：胶囊要么占宽、要么藏进浮层 |
| 成本 | 中 | 低 | 中 |

**推荐 A；C 作为二期可选**（胶囊只在"有查询词"时出现、放在浮层头部，不占工具条）。B 不建议。

### 6.3 结果面板

搜索框下方浮出（`position: fixed`，锚定搜索框；**不能放进 `.map-topbar`**）。桌面宽 380px；窄屏左右各留 12px、最大高度 45vh。

```
┌───────────────────────────────────────────┐
│ 点位 7 · 资产 3 · 轻资产 7      [清空]     │  ← 分组计数
├───────────────────────────────────────────┤
│ W12  员工D                    含 SSD ×1  │  ← 点位行
│   └ 命中：轻资产「M.2固态 宏碁N3500 SSD」  │
│ W07  空闲                       含 SSD ×1 │
│ A100-03-00038  ⊂ W09           资产编号   │  ← 资产命中（按点位聚合）
├───────────────────────────────────────────┤
│ 不在图上（3）                              │  ← 关键分组
│  · 员工B · 罗技MK270 键鼠 ×1   人持有      │
│  · 联想 ThinkPad E14 未挂点位   去资产页 → │
└───────────────────────────────────────────┘
```

- **行点击** → `centerOnStation(station)` + `select(station)`（打开右侧详情抽屉）。复用现有函数，不新写定位逻辑。
- **「不在图上」分组**：轻资产 → 跳 `/light/:categoryId`；资产 → 跳 `/asset/:id`。这一组存在的唯一目的是"不让搜索说谎"。
- **命中过多**：命中点位数 > 20 时，面板顶部提示「命中过多，再输入几个字」，仍高亮但不自动定位（避免每次按键地图乱跳）。
- **不自动定位**：只有"点击行 / 按 Enter"才移动地图。用户刚手动缩放过，不该被搜索抢走视图。
- **空结果**：`没有匹配` + 如果存在"不在图上"的命中，则照常展示该分组——这正是修复"以为搜坏了"的地方。

### 6.4 文案与占位

- placeholder：宽屏 `搜索姓名 / 点位 / 资产编号 / 轻资产`；窄屏（< 900px）退化为 `搜索…`（108px 宽度放不下，截断反而更糟），`title` 里给全量说明。
- 图例区的空结果提示保留，但改为「没有匹配的点位」→ **「没有匹配，图上无结果」**（和面板措辞一致，避免一处说"点位"一处说"结果"）。

## 7. 数据从哪来

前端本来就有全部点位；缺的两块**懒加载 + 缓存**即可，不需要新接口：

| 数据 | 来源 | 条数 | 取哪些字段 |
|---|---|---|---|
| 点位 | 已有 `stations` | 69 | `code` / `user_name` |
| 资产 | `GET /api/assets?page_size=1000` | 150 | `asset_code` / `finance_code` / `serial_number` / `brand` / `model` / `user_name` / `workstation_id` |
| 轻资产 | `GET /api/light/holdings?page_size=200` | 11 | `category_name/brand/spec` / `holder_kind` / `ref_id`（workstation→点位 id）/ `host_workstation_code`（asset→按编码查点位）/ `stock_location_station_id` / `user` / `quantity` |

- **触发时机**：搜索框第一次获得焦点时拉一次，缓存到页面生命周期。不搜的人零成本（地图打开不多两个请求）。
- **不加防抖**：数据在内存里，150 条算一遍是微秒级；防抖反而让输入有延迟感。
- **⚠️ 截断守卫（必须有）**：两个接口都有 `page_size` 上限（资产 1000、holdings 200）。若 `total > items.length`，面板底部必须写「共 N 条，仅索引前 M 条」——否则资产涨到 1200 台时搜索会**静默漏结果**，而界面上一切正常。这是最典型的假绿。

为什么不加后端搜索接口：
- 拼音匹配的实现只有前端有（`utils/pinyin.ts`，用 `pinyin-pro`），后端没有拼音依赖；搬到后端要么加依赖，要么两套匹配逻辑各算一遍（违反"同一个数只算一次"的项目口径）。
- 归属（配件挂在哪个点位上）该由后端决定，但这件事**已经算了**：`to_holder_out` 现读 `asset.workstation.code`、`to_holder_out` 对 stock 用 `_station_id_by_code` 解析 —— 接口已经把"在哪"给出来了，前端只做"用户敲的字命中哪些字段"。

**若将来资产上到几千台**，再新增一个精简的 `GET /api/workstations/search-index`（只返回 `{code, station_id, …}` 元组 + 后端解析好的 `station_id`），把"归属"固定在后端；匹配仍留在前端。现在做属于提前优化。

## 9. 分阶段

**一期（一个 PR，只动前端 `SpaceMapView.vue` + 3 个表单文件；无后端改动）**
1. 删 `room` 匹配 + placeholder + 空结果文案；
2. 懒加载资产/轻资产索引（含截断守卫）；
3. 搜索维度扩到 4 个，`matchedIds` 改为"按维度归因"的结构（`Map<stationId, Reason[]>`）；
4. 结果面板（点位/资产聚合 + 不在图上分组 + 点击定位）；
5. `room` 收口 5 处（第 8 节）。

**二期（可选）**
- 浮层头部的显式范围胶囊（全部/人/点位/资产/轻资产），只在有查询词时出现；
- 键盘 ↑↓ 选择、Enter 定位、Esc 清空；
- 命中点位角标改为"命中品类的件数"，而不是总件数（需先想清楚与"轻×N 总件数"语义的冲突，**待议**）。

**三期（另议）**
- 按底图分区搜索（命中测试）。

## 10. 验收怎么做（避免假绿）

反例先立着：当前 CHANGELOG 里那句"渲染 258 个 SVG、0 个空 path"就是假绿——只数已经存在的 svg，抓不到"本该是 svg 却写成文本"。搜索的验收同理，**不能数"亮了几格"**。

可复跑脚本（`.tmp/verify-map-search.js`，Playwright + 临时实例 8099 + 库副本，只读两红线：不点导出、不点新增/编辑/删除）：

1. **真值来自接口**：先 `GET /api/assets?keyword=某个真实编号` 拿到 `workstation_id`，再断言"图上被高亮的点位集合"等于该值（而不是写死 7 或 1）。
2. **轻资产维度**：`GET /api/light/holdings` 里筛 `holder_kind='asset'`，用 `host_workstation_code` 反查点位 → 去重得到期望点位集合；断言高亮集合一致，且面板「轻资产 N」= 该集合大小。
3. **不落点位分组**：期望条数 = `holder_kind='user'` 的条数 + 无点位资产命中数；断言面板"不在图上（N）"= 这个数，且图上**没有**为它们点亮任何点位（口径：不推断）。
4. **房间已移除（有分辨力的一条）**：真实库 1 个点位 `room='前台'`。改前搜「前台」高亮 1 个点位；**改后必须 0 命中**。这条断言只有在"确实删了 room 匹配"时才绿。
5. **布局红线**：390×844 下，面板打开时 `.map-topbar` 高度与打开前**相等**（证明浮层没挤进布局），且仍 ≤ 110、固定区 < 20%。
6. **截断守卫**：把索引接口的 `total` mock 成大于 `items.length`，断言面板出现"仅索引前 M 条"提示（否则这条防线的代码路径永远没人走过）。
7. **负向**：搜一个不存在的词 → 全部变暗 + 面板显示"没有匹配"；关掉轻资产图层后重复步骤 2，**结果必须完全相同**（证明搜索不依赖图层）。

## 附：与既有口径的关系

- 三个称呼不变：**资产点位**（正式）/ 点位（UI）/ `workstation`（代码）——本方案不改命名。
- 四态（有人 × 有资产）是**派生不落库**的；搜索结果同样不落库、不写任何状态，纯前端派生。
- 「使用人是展示信息，不是持有位置」的轻资产口径（设计 §2.4）直接决定第 6.3 节的「不在图上」分组：`holder_kind='user'` 的配件**不能**根据使用者名下的点位推断位置。
- 图层开关的既有定位（"只是标注，不筛选"，`1742`）本方案保持不变——这正是拒绝"绑图层搜索"的依据。

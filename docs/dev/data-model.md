> 13 张表 + 派生规则。**这里只写"结构长什么样、什么不能存"**，
> 接口怎么用看 [api.md](api.md)，轻资产单独一篇 [light-assets.md](light-assets.md)。

### 点位关系层：四色是**派生**的，不是存的（v2.1.0 定义 / v2.2.0 落地）

界面/地图上要能一眼区分点位处境。用**两个正交维度**派生：

| | **有资产** | **无资产** |
| --- | --- | --- |
| **有人** | ● 有人 + 有资产（正常在用） | ◐ 有人 + 无资产（人来了设备还没到） |
| **无人** | ○ 无人 + 有资产（公用/机房/会议室设备点） | · 无人 + 无资产（**规划位 / 备用桌 / 预留点**） |

**三条铁律**：

1. **颜色只是地图展示层的视觉规则，绝不可作为字段落库**。
   落库就等于把"当前概况"冻结成状态 —— 资产一挂上来状态就过期，
   而状态字段不会自己更新（本项目红线 2：一份数据两处存，迟早对不上）。
   正确做法是**每次渲染时现算**：`有人 = hasOwner(user_name)`、
   `有资产 = asset_count > 0`，两者一组合就是四态。

2. **「无人 + 无资产」不是无效点位。** 它是**合法且常见**的现状：
   预先规划的办公桌、备用位、会议室设备点、以后要放设备的位置。
   **UI 不把它渲染成"异常/警告"**，它就是 · 一个安静的中性态。

3. **不引入「点位状态」字段。** 已经有 `inventory` 的**盘点状态**（`checked` / `abnormal` /
   `pending` —— 见 `schemas_workstations.py`），那**是另一个维度**（"本次盘到哪了"，
   不是"这个点位有没有人/资产"）。两个维度各自独立，**别再合成一个状态字段**，
   否则将来做地图染色、盘点、活跃度、扫码都会被它绑死。

**为什么这么设计**：关系（有人 × 有资产）是**事实**，四态是**事实的投影**。
事实随时间变，投影随时重算 —— 这样后面加任何新玩法都只是在投影上多叠一层，
不需要迁移数据库。

#### 实现（v2.2.0）

唯一的派生入口是 **`utils/workstationMap.ts::relationOf(station)`**，
`RELATION_META` 是四态的**唯一文案/符号来源**（地图顶栏、图例、侧栏三处都读它，
不各写一份 —— 否则改了标签忘了改图例，图上就会出现一种颜色配一句对不上的说明）。

**视觉刻意只有两个色系**：蓝 = 有人、灰 = 无人，
"有没有资产"用**边框虚实**表达（实线 = 有资产、虚线 = 有资产缺失、点线 = 空置）。

> 为什么不给四种颜色：四个色相铺满一屏就是"彩色地图"，而这页的主角是**平面图**，
> 点位只是叠在上面的记号。四种都抢眼的结果是没人看得出格局，只觉得花。
> 「有人 · 无资产」用琥珀**虚线**而不是红色：它绝大多数是"还没配"而不是"坏了"，
> 刷一片红会让管理员以为出了事故。

**三个维度互不干扰**（可以叠加，不是三选一）：

| 维度 | 生效时机 | 落点 |
| --- | --- | --- |
| 搜索（点位 / 人员 / 资产编号+品牌 / 轻资产） | 任何时候 | `isSearchDimmed()` |
| 盘点状态筛选 | 仅盘点模式 | `isDimmed()` |
| 关系筛选 | 仅**非**盘点模式 | `isRelDimmed()` |

盘点模式下**关系层整个让位**：`rel-*` 着色类不加、`isRelDimmed` 恒 false。
两个维度都是"这个点位怎么了"，同时上色只会让人分不清格子在说哪件事。

**图例与筛选是同一个东西**：顶栏那四格既是"这一片现在什么情况"的答案（带计数），
也是筛选器 —— 点一格只亮那类，**再点一下取消**。左下角图例同步展示同样的四色。
理由：管理员看地图时要的是"一眼看懂 + 立刻钻进去"，多一次"去哪儿开筛选"的点击就断了。

**窄屏默认关闭关系层**：四个关系格在 390px 上必然折两行，实测把工具条撑到 117px、
固定区占比破 20%（`e2e-banner-nopoint-0930` C1/C2 卡的就是这两条）。
手机上这一页的主要用途是"拿着走到点位盘点"，格局统计是次要的；
开关仍然留着，想看格局的人点一下就能开（代价是多占一行，知情可选）。
**别把 `relLayer` 无脑改回常开** —— `e2e-station-relation-1002` F1/F2 会红。

**「有人」的口径只取 `user_name`，不取 `room`**：`room` 填的是「总经理办公室 / 前台」
这类**地点**，不是"这个位置归谁"。本节早期版本写的"有人 = room 或 user_name 有值"已修正 ——
真要用 `room` 表达"这位置已被预留给某个部门"，那该是第三个维度，不是这一层。

13 张业务表 + 一张迁移记账表（`schema_meta`）。**轻资产的 3 张表**（`light_categories` /
`light_holdings` / `light_movements`）在「轻资产」一节单独展开，这里不重复：

| 表 | 存什么 |
| --- | --- |
| `device_types` | 设备类型 + 类别（`host` / `display` / `other`，决定能不能参与配对） |
| `assets` | 设备台账。**`workstation_id` = 挂在哪个点位上**（可空，绝大多数资产没有点位） |
| `asset_relations` | 主机 ↔ 显示器配对关系。**解绑不删行**，改成 `active = false` 并记录解绑人和时间 |
| `asset_events` | 变更事件 —— **设备视角**的时间线 |
| `inventory_tasks` | 盘点任务（范围、发起人、状态、结束时间） |
| `inventory_items` | 盘点任务里的每台设备 + 结果。带发起时的账面快照 |
| `workstations` | 点位（资产空间地图）：编码 / 坐标 / 朝向 / 归属人 / 房间 / **`floor_map_id`**。**软删除，编码不释放** |
| `relation_exceptions` | **例外确认**：`(rule, workstation_id, asset_id)` + 确认时的**关系指纹**。关系一变指纹对不上，旧确认自动作废（不设 `resolved` 字段） |
| `floor_maps` | 平面图（底图）：名称 / 画布尺寸 / 网格 / **`layout` JSON（建筑图元）** / 是否默认。当前**恒为一张** |
| `audit_logs` | 操作审计 —— **操作者视角**。一次写操作一条，带操作人 / IP / 类型 / 对象 / 摘要 / 成败 / 明细 |
| `schema_meta` | 一次性迁移的记账表（key/value），只用来记「某个迁移已经做过了」 |

### 关于平面图：建筑图元存 JSON，不是表

`floor_maps.layout` 存的是 `{"schema_version": 1, "shapes": [...]}`。**图元（地台 / 走道 /
房间 / 墙体 / 前厅 / 入口）没有独立身份、没有引用者、永远整张一起编辑** → JSON 文档最自然。
点位不一样（有唯一约束、被引用、能单独改）→ 必须留表。**形态不同不是不一致**（决策 60）。

`workstations.floor_map_id` 指向平面图，`ondelete="RESTRICT"`：还有点位挂着的图删不掉。
**它是关系预留不是功能预留** —— 当前全库只有一张图，前端也没有任何多图的选择入口（决策 64）。

### 关于「资产在哪个点位」：只有一处真相

**`assets.workstation_id` 是唯一的落点。** 刻意**没有**建
`asset_workstation_bindings` 之类的中间表：

1. 关系是纯**多对一**（一台资产同一时刻只在一个点位上），一条外键就够；
2. 「资产在点位间流转」的历史由 `asset_events` 免费提供 ——
   `workstation_id` 在 `_TRACKED_FIELDS` 里，改一次就自动记一条时间线；
3. 点位下有几台资产是**派生查询**（红线 2），不落库；
4. 建绑定表就等于同一件事存两处，必然出现"绑定表说在 A、assets 说在 B"
   而没人知道该信哪个 —— 这正是决策 27 里拒掉拼音列的同一个理由。

`workstations` 表里**不存资产列表**。原型导出的 JSON 里那个 `assets` 字段是
本地演示数据，导入时被**显式忽略**（见 `services/workstation_importer.py` 开头的注释）。

### 关于 `audit_logs` 和 `asset_events` 的分工

这是本项目最容易搞混的一处，**两张表不能合并**：

| | `asset_events` | `audit_logs` |
| --- | --- | --- |
| 视角 | 设备（挂在某台设备下，给那台设备的时间线看） | 操作者（一次用户操作一条） |
| 触发 | 设备自身发生了变化 | 有人做了一次写操作 |
| 失败操作 | 不记 | **记** |
| 批量导入 30 台 | 30 条（每台各一条变更） | **1 条**（"导入"这一件事） |

合并成一张表，两个视角都会瘸：要么时间线被"导入"这种批量操作刷屏，要么审计丢掉"谁试过但没干成"。

`audit_logs` 刻意**不挂外键**（`target_id` 就是个裸数字），也不跟随级联删除 —— 资产被删掉了，
「谁删的」这条记录还得在，不然审计就是自欺欺人。

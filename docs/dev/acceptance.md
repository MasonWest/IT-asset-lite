### 三条口径（比数字重要）

1. **只读脚本**（打真实库安全的）：`v1xx` 之外的那些 + `station-relation` + `floor-legacy-parity`
   + `fresh-clone`。**跑之前先 grep 脚本里有没有 `POST`/`PUT`/`PATCH`/`DELETE`**，有就别打真实库。
2. **含写操作的脚本一律对临时库**：
   `cp backend/data/it_assets.db .tmp/verify-x/` +
   `IT_ASSET_DATA_DIR=<绝对路径> python run.py --port 8099`，
   cwd 必须是 `backend/`，且**必须后台运行**（`run_in_background=true`）。
   **临时验证一律另起 8099，绝不动用户 8080 上的实例。**
3. **`v102` / `v111` 不是只读脚本** —— 它们要复位数据才能有确定起点，
   对当前真实库跑会因为"配对池已空"而失败。**那不是 bug。**

### 断言的两条纪律（都是踩出来的）

- **别在断言里写死编号 / 条数。** 用户在自己机器上加点位、关掉一次盘点任务，
  都是**正常操作**，写死的 `=== 62` / `必须有 6 片 chips` 会集体变红 ——
  然后你就得花时间分辨"这是 bug 还是数据变了"。**能对账就对账**（跟接口比、跟"该渲染的"条件比）。
- **要空库的脚本，开头先断言前提成立**（不是就 `exit 2`），否则它会在上一轮残留的脏数据上跑，
  报出"看起来像 bug"的红。
- **假绿的断言比没有断言更糟。** 2026-10-16 发现**并已修**：`e2e-station-relation-1002.js` 的 B2
  （"目标格子的数量与图上亮着的格子数一致"）实际比的是 **亮着的关系"种类数"**（筛选后恒为 1）
  与**顶栏那个计数** —— 它在真实库上通过，纯粹因为真实库「有人·无资产」恰好只有 1 个点位。
  换个有 3 个的库立刻红（看着像回归，其实是脚本写错了）。
  **根因**：读数函数返回的是**以关系名为键的 map**，同类多个格子互相覆盖 ——
  连 B5/B6（"没有任何格子被变暗"）也只看到了**每类最后一个**格子。
  **修法**：读数改成**逐格数组**，B2 这才真的比格子数；另补 B2b（变暗数 == 总数 − 目标数）、
  B2c（非目标类一个不留）、C0（四种关系都得真实存在，C 段的前提）。
  并加自检开关 `E2E_MUTATE=undim-all|over-dim|wrong-kind`：**断言必须在错误实现下变红才算数**
  （实测三种 mutation 各触发 3–4 条 FAIL）。
  **写断言时问一句："它在什么数据下会红？"** 如果答案是"只有当那个数字恰好是 1 才绿"，
  那条断言钉住的就不是它声称的东西。**承载体要能区分"1 个"和"3 个"** ——
  临时库 `.tmp/relation-e2e/seed.py`（10 点位、目标类 3 个）就是为这一条建的。

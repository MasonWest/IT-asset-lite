# 轻资产实现

> 口径（业务侧怎么用）看 [../user/light-assets.md](../user/light-assets.md)，
> 这一篇是"改这块代码之前必须知道什么"。

### 轻资产：**当前分配记录 + 流转流水** 两张表，同事务双写（v2.9.0 全面整改）

键鼠套装、SSD、内存这类**不构成固定资产**的配件。**不并入正式资产表、不另建人员/点位表**，
其余全部复用现有体系（点位用 `workstations`、主机用 `assets`）：

| 表 | 职责 | 关键点 |
| --- | --- | --- |
| `light_categories` | 品类：名称 / 品牌 / 规格 / 单位 | **一张字典表** —— 不记数量、不记位置、不记模式。**`tracking` 已删除** |
| `light_holdings` | **当前分配记录**："现在在哪、有几件" | 一条 = **一个**持有位置 + 数量；四条**部分唯一索引**兜底 |
| `light_movements` | **append-only 流水**："怎么变成现在这样的" | 只增不删不改；`corrects_id` 串起"冲正"对；也是重建 holdings 的唯一依据 |

> **`light_items`（单件档案）与整套"数量 / 单件"双模式在 v2.9.0 被删除。**
> 我们追的是"2 条内存装在 A100 上"，不需要给每条内存一个身份；SSD 也像键鼠一样按数量管。
> 详见 `设计方案-轻资产管理模块-修订版.md` §1.1 / §8。

**持有位置四选一，一条记录只能有一个**：

| `holder_kind` | 什么时候用 | 例子 |
| --- | --- | --- |
| `asset` | 装在某台正式资产上的配件 | 2 条内存插在 `A100-03-00001` 上 |
| `workstation` | 固定放在某个工位用的 | 1 套键鼠放在 `W23` 工位上 |
| `user` | 专门发给某人、没有固定位置 | 3 套键鼠发给张三 |
| `stock` | 还没分配出去，在库房 | 5 个转接头备着（可带 `stock_location`，能分放多处） |

五条口径：

1. **当前状态落库（快照），不是每次重放**：列表页 / 详情页直接读 `light_holdings`；
   流水是"过去"，holdings 是"现在"，两者**同一事务写入**。
2. **`light_holdings` 只允许被 `apply_holding_delta()` 修改**，不暴露任何"直接改库存"的接口；
   每次写操作后断言**守恒式** `Σ holdings = Σ(入库+期初+盘盈) − Σ(报损+盘亏)`，破了整体回滚。
3. **使用人不是第五种位置，是展示信息**：持有位置是 `asset` / `workstation` 时，使用人**一律现读宿主**
   （`assets.user_name` / `workstations.user_name`），本表不另存；持有位置是 `user` 时**不带任何点位** ——
   **绝不**因为张三名下有工位就推断他的键鼠在 W23。
4. **宿主信息现读、快照进历史**：流水里存**当时的编码快照**（`from_ref_code` / `to_ref_code` + `*_ref_label`）。
   ⚠️ 本库主键**无 AUTOINCREMENT**（无 `sqlite_sequence`，id 会复用），
   所以**绝不能只存 id** —— 删一台建一台，新的复用旧 id，历史当场指错对象。
   （`stock` 的存放位置也复用 `*_ref_code` 承载，这样"库存分放多处"也能重建。）
5. **三种来源泾渭分明**：`manual`（日常）/ `opening`（期初确认，计入、必须填操作人）/
   `import`（历史导入，**只进历史不进当前账、不参与重建**）。
   **期初确认允许补录 / 重做**（`schema_meta` 里的标记只是界面提示，不是禁止再录入的开关）；
   日常数量修正走**有审计的盘点调整**（`adjust`，盘盈 / 盘亏）。

**前置提示，但绝不自动改归属**（全站一致原则）：

- **报废资产**（`assets.py::run_operation` 的 `SCRAP`）：机器上还有配件 → 409 列出清单；
  用户明确勾选「配件随设备一起报废」才在同一次确认里把它们报损，**默认一个字都不动**。
- **删除点位**（`workstations.py::delete_workstation`）：**直接关联**（固定放在这个工位上）**硬拦**，
  `force` 也过不去；**随主机关联**只提示不拦（配件仍正确归属那台主机，只是失去点位信息）。

**界面写入口只有一个，且每类持有给的动作不同**（v2.9.0 修正）：

- **登记流转对话框是唯一写入口**，先选"人话动作"（入库 / 发给某人 / 装到机器·放到点位 /
  换个人·换个地方 / 收回库存 / 报损 / 更换配件），由界面翻成 `(op, from_kind, to_kind)`。
- **品类详情「当前分配」每张卡片上的按钮按持有类型分工**，并**直达表单**（动作与来源都预选好）：
  库存 → 发给某人 / 装到机器·放到点位 / 报损；人手上 → 收回库存 / 换个人·换个地方 / 报损；
  机器上 → 收回库存 / 换个人·换台机器 / 更换配件 / 报损；点位上 → 收回库存 / 换个人·换个点位 / 报损。
  **库存行上没有「收回库存」**（它就在库存里），人手上 / 机器上没有「发给某人」（先收回或用转移）。
- ⚠️ 反过来也成立：**对话框只在"预置动作确实被应用"时才能直达表单**。
  资产详情页那条入口是**挂载时 `modelValue` 就已经是 true**，所以 `watch` 必须带 `immediate`，
  否则预置被静默吞掉、用户还是落在"选业务动作"那一屏（v2.9.0 之前一直是坏的）。

**轻资产在点位上的位置：四组，前三组确定、最后一组是推断**（v2.9.6，取代 v2.9.1 的角标图层）：

v2.9.1 曾在点位左上角标「轻×N」，要开一个默认关着的开关才看得到。**已整条删除** ——
不是"没人用"，而是**它表达不了语义**：`Σquantity` 聚合后每条记录的身份就丢了，
「轻×3」分不清是 3 套键鼠还是 1 SSD + 2 键鼠，而用户要问的是"这块 SSD 在哪"。

- **四个分组，一个实现**：`services/light.py::_station_light_rows()`。

  | 组 | 含义 | 确定性 |
  | --- | --- | --- |
  | `direct` | 固定放在这个工位（`workstation_id=本点位`） | 确定 |
  | `via_assets` | 装在那台主机上，主机**当前**在这个点位 | 确定（跟随主机） |
  | `stock` | 库存位置写的就是本点位编码 | 确定（东西确实在那儿） |
  | `via_users` | 记在某人手上，而此人名下有本点位 | **推断** |

- ⚠️ **`via_users` 绝不折进任何总量**：一件东西在张三的 2 个点位上都会出现，
  相加等于把 2 个候选当成 2 份实物。侧栏标题写「确定 1 件 · 另有 1 件可能在」，
  而不是「共 2 件」。`STATION_LIGHT_CERTAIN_GROUPS` 是这条约束的代码形态。
- **库存要算**（v2.9.6 推翻 v2.9.1 的 D3）：`stock_location` 写成 `W52` 且确有此点位 → 就在 W52。
  旧口径的现场是"搜 SSD 点亮 W52、点进去说这里没有轻资产"。换算统一走
  `station_ids_by_codes()`（顺带 strip 空格）。**匹配不上就是匹配不上，不猜。**
- **人持有按"该人名下的点位"推断**：1 个 → 点亮它；N 个 → **N 处都点亮**，
  每处写明「按使用人的 N 个点位推断（W52、W63）」；0 个 → 进「不在图上」。
  只靠推断亮起的点位画**虚线橙框**（确定命中仍是实线）。
  ⚠️ 占位符（`/`、`／`）不算人名 —— 用 `ownership.has_owner()`，与前后端其它地方同口径。
- **问题中心兜底**：规则 `light_user_station_ambiguous`（INFO）—— 某人持有的配件 + 此人有 ≥2 个点位。
  动作「去轻资产核对」→ `/light`。**这是兜底不是主入口**：地图/侧栏已经把候选标出来，
  它存在的意义是"别只存在于搜索里"（员工A多了一个工位，不会挑他搜索的时候发生）。
- **不做"弹窗让用户选点位"**：那个交互的实质是写库。加 `preferred_station_id` 等于造出
  第五种持有位置，会破坏"一条 holdings = 一个持有位置"的重建与守恒式断言。
  歧义就显示成歧义，要确定位置就走真实流转（有流水、可冲正）。
- **接口**：`WorkstationOut` **删掉** `light_direct` / `light_via_assets`（没有消费方的派生态
  只会变成下一次"两处数字对不上"的种子）；`HoldingOut` 加 `inferred_station_ids` /
  `inferred_station_codes`（仅 `kind='user'`），`StationHoldingsOut` 加 `stock` / `via_users`。
- 验收脚本 `.tmp/verify-v296-light-pos.js`（21 项，临时库，含一条"员工A持有键鼠"的播种数据）。
  ⚠️ 旧的 `e2e-light-map-layer-1016.js` 与 `e2e-light-layer-smoke-real-1016.js` **已过期**
  （它们点 `.light-toggle`、数 `.light-badge`），复跑必红，不要拿它们的红当回归。

**「按宿主浏览」时显示什么：主行 = 内容，副行 = 宿主**（v2.9.2）：

接口 `HoldingOut` 除了"持有位置"（`HolderOut` 那半边），**必须同时带品类**
（`category_name` / `brand` / `spec` / `unit` / 单行版 `category_label`）。理由见决策 87。

| 上下文 | 主行 | 副行 |
| --- | --- | --- |
| 点位侧栏「固定在此工位 / 随主机上的」 | **品类名** | `品牌 规格`（+ 随主机那组带「装在 XXX 上」） |
| 资产详情「关联轻资产」 | **品类名** | `品牌 规格 · YYYY/MM/DD 装上` |
| 台账页 / 流水页 | 宿主（`display`） | — |

⚠️ 台账页与流水页**保持显示宿主**：那是"按品类"的上下文，品类从标题已知，宿主才是信息。
**同一个字段在两个上下文里该显示什么，取决于那个上下文里"什么还不知道"。**

- 两个上下文都**只答"是什么 + 在哪"**，都不进任何资产统计口径。
- ⚠️ 「+ 登记配件变动」这类"图标 + 文字"的按钮必须 `display: inline-flex`（见决策 88）。

**台账页的两种排法共用一套视觉语言**（v2.9.3，见决策 90）：

卡片网格（默认）与「列表」视图只是同一份数据的两种排布 —— 品类图标、状态胶囊、
持有 chip、数字单位**都是同一批实现**，切来切去不该像两个系统。
列表视图**不许用** `el-table` 的 `border` / `stripe`（满屏网格线 + 斑马纹，
与全站"不要密集后台表格感"的取向直接冲突）：无外框、无竖线、无斑马纹，
外面包一层 `.panel` 白面板，行可点进详情。
⚠️ 「未登记」（`pending_opening`）是**状态、不是数字 0** —— 用琥珀胶囊，别渲染成灰色的 0。

**登记流转的数量默认恒为 1**（v2.9.3，见决策 89）：从某条持有记录发起时不再跟随那条的数量，
但会在数量框下面写出"来源共 N 件、整条处理请改成 N"。信息给到，决定权留给人。

**运维脚本（三个，全部默认干跑 + 写前备份 + 拒绝打非临时库）**：

| 脚本 | 用途 |
| --- | --- |
| `backend/migrate_light_v2.py` | 老库迁移：按有效流水建 holdings → 逐条核对旧单件档案 → 删 `light_items` → 删 `tracking` 列 |
| `backend/light_check.py` | 一致性体检：**只检查、不修复**（退出码 1 = 有差异） |
| `backend/light_rebuild.py` | 重建 holdings：默认只出差异报告；`--apply --confirm` 才写，且先备份 |

⚠️ **`light_movements.item_id` 必须连外键一起删**（与设计 §8.3 的取舍不同，已实测确认）：
它上面有 `REFERENCES light_items(id)`，而 `light_items` 要删 —— 父表不存在之后，
**任何一次对 `light_movements` 的写入都会报 `no such table: main.light_items`**。
真实库那张表用的是**表级外键**写法，SQLite 的 `DROP COLUMN` 拒绝对它动手 → 迁移走「重建表」，
新表 DDL 由 SQLAlchemy 模型编译（不手写）。

`asset_events` **装不下轻资产**：它的 `asset_id` 是 NOT NULL 外键，每条事件必须挂在某台正式资产上；
而配件可能在主机流转前后拆卸/更换，其历史必须独立记录。
`/api/light` 独立前缀，不挂 `/api/assets` 下。

# 决策 · 点位的派生状态与护栏

| # | 决策（短标题） | 理由 / 代价 |

| 71 | **点位四态（●◐○·）是渲染时派生的，不落库**（详见第五节「点位关系层」） | 曾经最省事的做法是给 `workstations` 加一个 `status` 字段存"四选一"，但那样等于把**时刻变化的概况冻结成事实**：资产一挂上来字段就过期，而字段不会自己更新（红线 2）。正确做法是渲染时用 `有人 = hasOwner(user_name)` × `有资产 = asset_count > 0` 现算。**⚠️ 与盘点状态是两个维度**：`inventory` 那套 `checked/abnormal/pending` 回答的是"本次盘到哪了"，与"这点位有没有人/资产"无关，**别合并成一个状态字段**。**「无人 + 无资产」是合法现状不是异常**（规划位/备用桌/预留点），UI 不渲染成警告色。 |
| 72 | **地图只用蓝（有人）+ 灰（无人）两个色系，"有无资产"靠边框虚实区分**（v2.2.0） | 最初的想法是"四态就配四种颜色"，结果一屏四种色相直接变成**彩色地图** —— 而这页的主角是**平面图**，点位只是叠在上面的记号；四种都抢眼的后果是没人看得出格局，只觉得花。收成两个色系后：蓝=有人在用、灰=没人（或公共设备），"有没有资产"用实线/虚线/点线表达，四个状态在 80×56 的格子上依然分得清。**「有人·无资产」用琥珀虚线而非红色**：它绝大多数是"还没配"而不是"坏了"，刷一片红会让管理员以为出了事故 —— 同一个"不要用警告色说中性事实"的道理，跟 `use_name='/'` 不显示成蓝色人名标签是同一条。**⚠️ 判定"是不是灰"看色度（max-min）别看绝对相等**：Tailwind slate 系天生带一点蓝（`#cbd5e1` 差 22），要求 r=g=b 会把中性灰全判成有色。 |
| 73 | **空库不塞默认底图**：真·空库时 `floor_maps` 留空，画布是空白虚线 + 三步引导（v2.3.0） | 起因是站在"全新 clone 的人"视角真走了一遍，发现他打开地图看到的是**本项目办公室的布局**：「总经理办公室 / 直播间 / 大会议室 / 中央走道」—— 而 `DEFAULT_FLOOR_LAYOUT` 被 `init_db()` 无条件写进每个新用户的库。**这等于假装知道对方公司长什么样**；更糟的是 `floor_maps` **没有删除接口**（只有 `PUT`），新人唯一出路是进编辑器把 19 个图元逐个 Delete 掉再重画。**判据是「整个库一条业务数据都没有」（`_database_is_completely_empty`）而不是「`floor_maps` 空不空」** —— 后者是**结果**不是原因："老库升级该补图"和"新用户刚起步"在这一行上长得一模一样，混淆两者就会漏掉老库的 `floor_map_id` 回填。**⚠️ `_recognize_default_floor_map` 绝不能删**：它同时是老库升级补 `floor_map_id` 的唯一路径，删了老用户会掉进"点位还在但不属于任何图"的状态（第五阶段）。只在它前面加一个前置短路。**⚠️ 短路时刻意不写 `DEFAULT_FLOOR_MAP_KEY` 记账**：那把钥匙的意思是"默认图已认领"，而这里的事实是"从未建过图"，写了将来用户自己建图后会被记账分支误判成"被 reset 清过"而不再认领。**⚠️ 不给已有库做迁移**：有图的老库照旧一张不少，判据本身保证了这点（验证见第十节 `e2e-fresh-clone-1005` C1~C7）。 |
| 74 | **空画布引导的消失判据只有「他建出东西了」这一条**（v2.3.0） | 第一版把 `editMode` 也算进 `isBrandNew` 的条件里，于是用户点「开始建点位」进了调整位置模式的**瞬间引导就消失** —— 而这时他一个点位都还没建，正是最需要指引的时刻。**引导说的是"这里还什么都没有"，不是"你现在没在做什么模式"。** 现在条件只有 `图元数 === 0 && 点位数 === 0`，落下第一个点位它自然消失。**配套：进了调整位置模式后引导缩到一半宽、让到画布上方**（`align-items: flex-start`）—— 用户在干活时它该退居二线，而不是继续占据 C 位挡住他要点的画布。**⚠️ 它是浮层且 `pointer-events: none`（只有两个按钮恢复点击）**：提示不是必须先关掉的弹窗，用户自己动手了它不许挡路。 |
| 76 | **「什么算有人」前后端必须同口径，且后端的"没设备"不叫 `empty`**（v2.4.0） | 起因是加对账脚本时量出来的**真差异**：后端 `assigned` 用最朴素的判据`user_name.strip()`，前端 `hasOwner()` 则把「`/`」和「`／`」算成**没归属** —— 项目自己早就认定「斜杠 = 没填」（真实库**资产**表里就有 15 台写的是 `/`），但那个认定**只在前端实现了**。真库点位表此刻恰好一个斜杠都没有，所以两边数字一样、**差异是隐形的**；哪天有人往点位表填一个 `/`，后端就报「已分配 +1」而界面显示「未填使用人」，**同一页上两个数字打架且零报错**。**修法**：后端加 `services/ownership.py`（判据的唯一出处），两边对账由 `backend/check_ownership_parity.py` 守住 —— 它**读前端 `format.ts` 真实源码**抠出 `NO_USER_MARKS` 字面量逐条比对，**不在浏览器里复刻一遍前端逻辑**（自己抄自己，抄错了一起错，测试照样绿）。**⚠️ 顺带发现一个更隐蔽的命名陷阱**：接口的 `empty` 算的是「**一台设备都没挂**」（资产轴），而前端的「空闲点位」是 `total - assigned`（**没人用**，人员轴）—— **两个字段都叫"空闲"，指的却是两件事**。已把后端字段改名 `without_asset`（名字自带语义、不依赖读文档）。**别拿这两个数互相对账**（我就先写错了一次，报出一个"界面 3 vs 算出 4"的假失败）。 |
| 77 | **画布护栏：把缩放上下限与步长钉成契约，不抽 composable**（v2.4.0） | 用户问"要不要抽手势逻辑"，**评估结论是不抽**（理由见决策 76 的姊妹条 / 第八节「为什么没抽手势」一节）：纯手势只有 **234 行**，`onStageClick` 直接调 `createStation`（写库 + 审计 + 撤销栈）、`canPan` 读 `adding/editMode` —— 抽出去要传三个回调进去，那是**假分离**：文件是分开了，风险一分没减，却多了一层间接。真问题是"**改它的时候怕碰坏别的地方**"，而抽文件**解决不了**那个（抽完之后改的照样是同一套逻辑，只是换了个文件住）。**真正对症的是护栏**：把 `MIN_SCALE/MAX_SCALE` 与两个缩放步长固化成具名常量，并用 `e2e-canvas-guardrail-1008.js` 把它们**钉成契约**（改了值就红，并在信息里说明"你改了行为，是有意的吗"）。**它不禁止你改，只让改动必须是有意识的** —— 实测把步长从 1.15 改成 1.3，立刻两条断言变红。⚠️ 顺带钉住一条早就该钉的：**视觉网格必须 == 吸附网格**（20px），原型踩过"画的 20px、吸附按 4px，肉眼看不出对齐"这个坑。 |
| 78 | **「新增点位」不许被房间拦住，新增态下也必须能平移**（v2.4.1，真实用户报障） | 用户原话：「点新增工位，然后点击地图上需要新增的点位，但是工位死活新增不上去」「不管是不是在调整位置模式」「之前新增就很困难，有时点几下能出来，有时死活出不来」。**报障人怀疑「新增」和「调整位置」两个按钮冲突 —— 不是**，实测两个状态完全独立（`adding` 与 `editMode` 是两个 ref，按钮各调各的）。真凶是两条：① `onStageClick` 里 `if (target.closest('.ws') || target.closest('.room')) return` —— `.room` 是**纯装饰的房间矩形、没有任何点击行为**，排除它没有任何好处，坏处却是**房间就是桌子所在的地方**：真实库 8 个房间盖住画布一大半，实测采样 40 个点 **20 个（正好一半）落在这类元素上，点下去静默无反应**；② `canPan()` 里 `if (adding.value) return false` 一刀切 → **新增态下地图完全拖不动**，想加一个视野外的点位得"退出新增→拖地图→再进新增→再点"四步。**修法**：房间不再拦截；新增态下空白处允许平移，同时加 `movedDuringPan`（阈值 6px）挡掉"拖完松手浏览器补发的 click"，避免误建。**⚠️ 更该记住的是第三条：静默失败**。上面两种情况下用户点了三五次，界面**一个字反馈都没有**，只能猜"是不是坏了"。现在点已有点位会说"这个位置已经有点位 Wxx 了，想加新的请点空白处"（提示放在 `select()` 里而不是 `onStageClick` —— **`.ws` 上有 `@click.stop`，事件根本冒泡不上来**，第一版放错地方成了死代码）。 |

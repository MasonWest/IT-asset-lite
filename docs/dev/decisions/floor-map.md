# 决策 · 平面图与批量生成

> 覆盖：图元存 JSON / 编辑器独立页 / 单图心智 / 批量生成的防护与审计
> 回到 [决策索引](README.md) ｜ 原文快照：`docs/archive/CURRENT_STATE-v2.9.10.md`

| # | 决策（短标题） | 理由 / 代价 |
| --- | --- | --- |
| 60 | 平面图**图元存 `floor_maps.layout` JSON，不建 `map_shapes` 表**；但**点位必须留表** | 图元是"纯几何 + 一个标签"，**没有任何东西引用它们**、永远整张一起编辑 → JSON 文档就够，建表只会换来一堆"删图元要先删关联"的伪问题。点位相反：有 `code` 唯一约束、被 `assets.workstation_id` 引用、能单独增删改 → 必须留表。**形态不同不是不一致**。对照 `asset_events.detail` 用 Text 不用 JSON 列 |
| 61 | **不加桌椅图元**（原型里的 `.f-tbl` / `.f-seat`） | 加了就等于承诺"这个编辑器能画办公室家具"，滑向"办公室 CAD Lite"。图元是**空间骨架**（地台 / 房间 / 墙体），桌椅是填充物 —— 这条线必须在第一次就划死，否则下次就是"加个绿植吧"。原型里那两件也够不上可用：只是两个灰块 |
| 62 | 编辑器做**独立页 `/map/editor`**，不做 `/map` 上的模式开关 | `/map` 手机端顶部固定区压到 17.7% 后画布只剩 674px，再叠一条绘图工具条就没了。且"编辑底图"与"看地图"是两件不同的事 —— 做成同一页的模式切换，用户只想看看时误触改坐标的概率不低 |
| 63 | **图元删除不弹确认**，只提示"已删除（Ctrl+Z 可撤销）"；**通用原则：可撤销的操作不拦，不可撤销的才拦** | 原方案写的是"删除图元要确认"，评审时被指为实际缺陷：图元活在内存文档里，`Ctrl+Z` 分分钟能回来，弹确认纯属打扰（模型越用越烦，最后条件是反射性点确定，等于没有）。真正该拦的只有**回不来的**：离开页面且有未保存改动、删除整张平面图 |
| 64 | **单图心智模型**：后端有 `map` 概念，**前端只能有"这一张图"的概念**；`floor_map_id` 是**关系预留不是功能预留** | `GET /api/floor-maps` 的 list **恒为一张**，且前端禁止出现选择器 / `?map=` / `maps[]` / 多图 Tab。防的是滑向「数据库支持多图 / API 半支持多图 / 前端假装支持多图 / 业务其实单图」—— 那种状态下复杂度凭空增加，而没有一条业务需求是真的需要它。将来真做多图，改接口那一层（放开 list、加 `?map=`）就够了，数据不用迁。守这条线用 grep：E3 之前前端源码里不该出现 `map_id` 字符串 |
| 65 | 批量生成的**编码真相在后端**，前端面板显示的号段只是"预期"；**撞号 409，绝不静默跳号** | 前端如果要"先看看最大的是多少再 +1"，两个人同时点生成就会撞出同一段编码。后端在同一个事务里查全量 `code` 再分配，唯一约束兜底。**跳号是更坏的选项**：界面上写着"将生成 W63~W86"、实际却因 W70 被已删点位占着而生成 W63~W69+W71~W87，用户拿这个号段去贴标签就会贴错 —— 因为有「已删点位编码不释放」这条既定设计（决策 25 一脉），号段必须与实际严格对应 |
| 66 | 图标级的"整图固定件"（`entry` 大楼入口 / `corrtext` 走道文字）**不给新增入口**，只在图元列表里可选中可删 | 它们带内联 SVG 或垂直文字排版，是装饰不是几何。放进"新增图元"面板会让人以为可以批量加十个入口，而数据里只存 x/y（SVG 仍写死在模板）—— 那会变成"加了个入口但画不出来"的悬空功能。**能给的数据化才是数据化**，其余保持原样 |
| 67 | **「批量生成点位」放在地图页「调整位置」里，不在底图编辑器里**（用户原话："底图是底图，工位是工位" —— 本表保留原话用词；v2.1.0 起统一叫「点位」）；生成是**立即写库**，故配三层防护 | **真实事故**：用户在编辑器里点「生成点位」试了试，以为跟新增图元一样"不保存就白搭"，退出时 `hasUnsaved=false` 所以**连离开确认都没弹**，24 个点位已经落库。根因不是忘记保存，而是**两个按钮长得一模一样、语义却相反**（新增图元 = 进草稿 `PUT` 才落库；批量生成 = 立刻 `POST` 落库）。**修法（2026-10-02 二次收口，用户提出）**：① **把点位相关的一切整个搬出编辑器**，收进点位自己的家 —— `/map` 的「调整位置」模式（那里已有单点新增/删除/拖动，全部"立刻生效"），歧义从根上消失，不再需要用户做"这个是草稿还是立刻"的判断题；编辑器里彻底移除。② 事前 `ElMessageBox.confirm` 说清"会立刻写进数据库"（面板常驻黄色警示条）。③ 事后「撤销生成」走 `DELETE /api/workstations/{id}` 软删除。**撤销 ≠ 批量操作**：撤销 N 个 = **N 条 `workstation_delete` 审计**（生成仍是 1 条 `workstation_create`），不做批量删除接口。**不做草稿制**：点位是表数据、有唯一编码约束，塞进 layout 草稿要引入"待创建点位"临时态，改动大且会污染编码分配逻辑。**通则**：一个界面里绝不混放"草稿型"与"立即生效型"操作 |
| 68 | 批量生成**不代填 `floor_map_id`**，点位归属仍由图保存时统一决定 | 生成时带上当前图 id 看似更贴心，但会和"点位归属由保存底图决定"这条既有口径打架：同一批点位，生成时挂在 A 图、之后用户改了主意在 B 图上保存布局，归属到底听谁的？**让归属只有一个决定点**（保存布局那次 `PUT`），比在两个地方各自维护更不容易出错。代价是刚生成的点位短暂"无图"，但它在全库可见、在图上也能渲染（前端按坐标画），看不出差别 |

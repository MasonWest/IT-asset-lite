| 80 | **关系核对是"每次现算的派生结论"，唯一落库的东西是「例外确认」这个业务决定**（v2.5.0） | 规则的唯一实现在 `services/relation_check.py`（纯函数、零 IO，连改数据的能力都没有），接口层只负责取数 + 叠例外。**刻意不建"问题状态表"**：核对结论跟地图四态关系层（决策 71）是同一条原则 —— 资产一挂一摘结论就变，落库必然过期且无人更新（红线 2）。**四种状态里只有 `mismatch` 需要人看一眼，而它不是错误**：`unregistered`（某一侧没登记使用人）明说"这在业务上是正常的"，**尤其"点位没人 + 挂着有主的设备"（公共设备/备用机/会议室机器）不许判成错误** —— 一上来就刷红，用户第一次用就会把这功能关掉。所以配色走琥珀、不走红，文案里必须出现"系统不会自动改任何一侧"。**例外确认存 `sha1` 指纹而不是状态字段**：`fingerprint = f(station_id, 点位使用人, 资产 id, 资产编码, 资产使用人)`，下次核对指纹对不上 → 这条确认**自动失效、差异重新冒出来**（要求：旧例外不得继续掩盖新差异）。指纹里必须带 `asset_code` —— 主键是 `INTEGER PRIMARY KEY`（非 AUTOINCREMENT，见 `reset.py`），删末行之后 **id 会被复用**，只记 id 会让旧例外挂到一台新设备上。**`user_name` 里插进数据库的人名与编码要先转义再渲染**（前端 `richText()`），后端文案里的 `**粗体**` 是最小渲染、不引 markdown 库 |
| 81 | **迁移走独立路由 `/api/relocations`，且用「预览令牌」同时挡并发改动与重复提交**（v2.5.0） | **为什么不并进 `/api/transfer`**：那个前缀是**导入导出**（改"台账里有哪些设备"），这里改的是"设备摆在哪 / 这个位置归谁"。名字里都有"迁移"，语义完全不同 —— 塞一起的最坏后果是有人对着"迁移"按钮点下去，实际触发了一次批量导入，**不可逆**。**三种"位置"必须分开**（CS 决策 67 那类事故的预防）：地图上拖格子 = `PATCH /api/workstations/layout` 改 `x/y`（纯排版）；资产换点位 = 改 `assets.workstation_id`；点位业务迁移 = 上一项 + 点位使用人（+ 可选退役源点位）。`relocation.py` 的产物里**刻意没有 x/y/facing 字段**，并用单测 `test_never_touches_coordinates` 钉住 —— 这条不能靠自觉。**令牌 = `sha1(mode, 目标点位快照, 选中的设备快照)`**：预览到执行之间只要有人动了这些对象，令牌就不一样 → 409 逼用户重新预览。**禁用按钮挡不住并发改动和连点两次，令牌能**，而且一条机制同时覆盖这两件事。执行在**单事务**里，任一步抛错整体回滚，不留"搬了一半"；**一次操作 = 1 条 `relocation_apply` 审计，但每台设备各写 1 条 `asset_events`**（设备履历要各自完整，与批量导入同口径）。**绝不自动推断使用人变更**：搬设备只改 `workstation_id`，预览里明写"不改设备使用人" |
| 82 | **「归属会不会跟着走」是派生结论，不是"勾没勾"本身；预览必须把"不会变的东西"也说出来**（v2.5.1） | 两个连着的教训，都出在「点位业务迁移」上。**① 判据必须走唯一实现**：规划器里判"有没有人"曾经用自写的 `(user_name or "").strip()`，**直接违反决策 76** —— 源点位写 `/`（= 没填）时它是个真值，于是 `/` 被当成**一个真使用人**，勾上「迁移点位使用人」执行会把**目标点位的人覆盖成 `/`**（归属丢失），而同一份预览还写着"实际不会改变任何东西"。现在一律 `services/ownership.py::has_owner()`，且**源点位没有归属就一个字都不写** —— 拿"空"去覆盖目标不是迁移，是丢归属。**凡是"有没有人"的判断，新代码再写一次 `strip()` 就是 bug。** ② **"不变的"也要说**：接口一直是对的（审计里 `move_user: false` 摆着），错的是**预览只说会变的东西** —— 用户做完 `W46 → W47` 的整体迁移，发现使用人没动，只能去翻审计日志才知道"那项没勾"。现在预览常驻一块**「点位归属」**，源、目标两侧都把 `迁移前 → 迁移后` 摆出来，不变的显式标「不变」，并给出"想搬就勾哪一项"的指引。配套：`user_move` / `{source,target}_user_{before,after}` 结构化下发（**勾没勾、甚至校验有冲突时都算出来**，不让接口悄悄回 `null`）；**`notes`（只说明情况）与 `confirmations`（必须点头）分开** —— 说清一件事不该顺手加一次确认负担。**通则：预览的职责不是"列出改动"，而是"让用户在点执行前就能预测结果"；只说会变的那部分，等于把另一半留给审计日志。** |
| 83 | **问题中心是"检查引擎的一个视图"，不是一张表；`key` 与 `fingerprint` 必须分家**（v2.6.0） | `GET /api/insights/issues` **只读、不写审计、不落库** —— 直觉做法（建 `issues` 表存待办 + 状态）是错的，理由与决策 71 / 80 同源（红线 2：投影存下来必然过期）。**"处理结果"靠事件驱动**：用户点了动作去做真实操作，操作本身写审计与事件，下次算的时候那个条件自然不成立 —— **这就是"处理后问题消失"的物理解释，不需要"已解决"字段**。**三个计数的定义写死**：`by_rule.count`（该规则全部，**含**已确认例外）/ `handled_count`（其中被**有效**例外盖住的）/ `total = Σ(count - handled)`；**已确认的例外不计入待办，但仍可查看、可撤销**。**⚠️ `key` 与 `fingerprint` 是两件事**：`key = <rule>:<scope>:<对象 id>` 只随**对象身份**变（去重 / 定位 / 跨页面一致 / 分页稳定），`fingerprint` 随**关系状态**变（只用于判"例外还算不算数"）。拿 fingerprint 当标识的后果是"用户改一下使用人，同一条问题就换了身份"。**排序必须稳定**（`severity desc, rule asc, key asc`），否则分页漏条 / 重条。**动作 URL 只由后端规则模板生成并过白名单**（`ALLOWED_ACTION_PATTERNS`），不回显任何外部输入；落点不一致时**不给组级入口**（否则一个按钮会把一批人导到同一个地方）。**排除项与纳入项一样明确**：点位没人但有主的设备（合法现状）、字段完整度类问题（一进来就是 148 条）**一律不进** —— 问题中心的价值取决于"进去的都是值得看一眼的"，不是"什么都收" |
| 84 | **时间线补口：迁移用专属事件；例外进的是"设备级"履历；"失效"不写事件**（v2.6.0） | ① 迁移写 `relocate` 而不是通用 `update`（一次搬十几台，履历上该一眼可辨）。② 例外确认 / 撤销给**对应那台设备**补一条 `relation_exception` —— 看履历的人有权知道"它当初被认定过是合理的、理由是什么"；只看"确认"不看"撤销"的履历是残缺的。⚠️ ③ **只有设备级的例外进履历**：点位级（`asset_id=0`）没有对应设备，写不进 `asset_events`，它在点位侧栏的例外表里呈现 —— 不为了"齐全"而挑一台代表设备去挂，那是为满足表结构编造事实。⚠️ ④ **"例外失效"不写事件**：失效是**算出来**的（存下来的指纹 ≠ 现算的指纹），落库就违反红线 2。时间线上有"确认"而没有"失效"是**正确**的，不是漏了 —— 别顺手补一条"失效事件"。⑤ **没动时间线本身**：`eventMeta()` 本来就有未知类型的兜底，筛选条是从返回数据现生成的，所以加事件类型不需要改时间线渲染（决策 70：不改历史文案） |
| 85 | **关联建议是"算出来的临时结果"，与问题中心共用归属口径；执行前必须重检**（v2.7.0） | ① **建议不落库**（红线 2）：没有建议表、没有"已忽略"状态，关掉面板就是暂不处理，差异留给问题中心。② **单台结论的唯一实现是 `services/link_suggestions.py::suggest_for_asset()`**，判空只走 `has_owner()`（决策 82 的复发形态防在这：新代码再写 `strip()` 判"有没有人"就是 bug）。③ **`公用` 只在建议层单独认**（`SHARED_MARKS`）：全局 `has_owner('公用')===true` 不变，改它是一轮独立决策 —— 两套口径的分歧是**有意的**，单测钉住。④ **执行前重检**：弹窗打开期间资产可能被改，`apply-linkage` 在写库前逐台重算 suggestion，不再是 `fill` 的跳过（`state_changed`）—— 过时的检查结果直接批量覆盖 = 拿旧世界覆盖新世界。⑤ **预检只服务「无归属 → 有人」一个方向**（有人点位 409、占位符 400）：换人 / 绑定 / 迁移三个方向刻意延后（**清人已于 v2.7.1 补齐**，见决策 86），第一期硬塞四个场景等于四个弹窗骚扰源。⑥ **conflict / keep 默认不勾**：不替用户做覆盖决定，"点位使用人变了资产必须跟着变"这条规则被刻意排除（决策 80 同源：差异不是错误） |
| 86 | **关联建议只做"事后没人兜底"的方向；扩场景的准入判据写死；清人与迁移解耦**（v2.7.1） | ① **准入判据**（扩场景的唯一标准）：**只在一个动作会让另一半事实“变得明显错误、或者变得看不见”时才提示**。按真库 204 条审计实测：清人 3 次发生（残留的人名**问题中心抓不到** —— `station_vs_asset_user` 要求两侧都有人、`asset_user_unregistered` 要求点位有人）→ ✅ 做；换人 **0 次**（98% 一致率 → 一次弹 2 台且倾向全勾，噪音高于收益）→ ⏸；绑定到有主点位 16 次但命中率 ≈ 0.5%（与问题中心重复）→ ⏸；迁移到有主点位 **0 次**（v2.5.1 的迁移预览已承担该职责）→ ⏸。② **清人默认一个都不勾**：它是“丢归属”方向，且设备很可能属于岗位而非个人（人走了、机器留给下一任）—— 勾了才清，不勾就是保留。③ **执行接口不接人名**：清谁由服务端读点位**当前**使用人决定（客户端传人名 = 可能清错人）；重检条件与填人相反（要求仍登记为被清那位，否则 `state_changed` 跳过）。④ **与迁移彻底解耦（用户原话“各干各的”）**：解耦靠**源码断言**守（`TestDecoupledFromRelocation` 读两个迁移模块真实源码，断言不含 `link_suggestions` / `build_clear_suggestions` / `apply-unlink` / `asset.user_name =`），不靠自觉。⑤ 审计 `asset_unlink` 与 `asset_linkage` **分开**：方向混在一条里等于要读 summary 才知道是“给”还是“拿”。 |

# 备份、恢复与维护命令

> 这一篇是"动手改数据"的动作。只想日常用系统的话，看 [资产台账](assets.md) 就够了。

## 备份与恢复

双击 `backup.bat`。它会打印出数据库文件和备份目录的完整路径，一眼能看清东西在哪：

```
数据库文件：D:\你的目录\backend\data\it_assets.db
备份目录  ：D:\你的目录\backups

[完成] 已生成备份：it_assets_20260924_101100.db
       大小 192.0 KB，包含 10 台设备
```

它走的是 SQLite 的**在线备份接口**，服务正在运行、有人正在录入也能拿到完整一致的数据（直接 copy 文件在写入时有概率拿到写了一半的页面）。备份完会做一次完整性校验，校验不过会删掉那个文件并报错 —— 不会给你留个 0 字节的「成功备份」。默认只保留最近 30 份，更早的自动清理。

命令行等价写法（想改保留份数时用这个）：

```bash
python backend\backup_db.py --keep 100
python backend\backup_db.py --list        # 只看不建
python backend\backup_db.py --out D:\bak  # 换目录
```

**恢复**：停掉服务，把 `backups\it_assets_xxxx.db` 复制成 `backend\data\it_assets.db`（覆盖），再启动。恢复前建议先把当前那份改个名留一手。

## 数据初始化：删库重启 = 空库

数据库文件在 `backend/data/it_assets.db`，首次启动自动建表。

**启动时不写任何业务数据。** 只会初始化设备类型这种字典数据（6 种）—— 没有它就没法录资产，它是系统能跑的最小前提。所以删掉 `.db` 重启，得到的是一个真正的空库：设备类型在，一台设备都没有。

| 时机 | 做什么 | 怎么触发 |
| --- | --- | --- |
| 每次启动 | 建表 + 轻量迁移 | 自动 |
| 每次启动 | 空库时建 6 个设备类型（字典数据） | 自动 |
| 每次启动 | **不碰任何资产数据** | — |
| 需要时 | 灌 10 台演示设备 + 配对 + 履历 | `python backend\seed.py` |
| 需要时 | 按编号规则批量补主机↔显示器配对 | `python backend\link_monitors.py` |
| 首次 / 灾难恢复 | 灌入点位数据（资产空间地图） | `python backend\import_workstations.py` |
| 首次 | 按使用人把「1 主机 + 1 显示器」的资产关联到点位 | `python backend\link_workstations.py` |
| 需要时 | 清空全部业务数据（保留表结构和字典） | `python backend\reset.py` |

**为什么演示数据不自动灌。** 一是分不清「库里这些设备是我录的还是系统送的」；二是误删数据库文件后重启会凭空"长"出十台假设备，跟真实数据混在一起，比没数据更糟。改成手动触发，灌不灌你自己说了算。

## 四个维护命令

```bash
python backend\seed.py              # 灌演示数据
python backend\seed.py --check      # 只看各表现在有多少条，什么都不写

python backend\link_monitors.py                # 批量配对：只看计划，不写库
python backend\link_monitors.py --yes          # 先自动备份，再实际写入
python backend\link_monitors.py --suffix=_M    # 改后缀（默认 -M）

python backend\import_workstations.py                # 灌点位：只看计划，不写库
python backend\import_workstations.py --yes          # 先自动备份，再实际写入
python backend\import_workstations.py --file x.json  # 指定别的点位文件

python backend\reset.py             # 自动备份 → 列出将删除的内容 → 输入 RESET 确认 → 清空
python backend\reset.py --check     # 只看会删掉什么，一个字都不写
python backend\reset.py --yes       # 跳过手动确认（给自动化脚本用）
python backend\reset.py --no-backup # 不先备份（不推荐）
```

四条命令都**幂等且不碰已有数据**：`seed.py` 只在对应表**完全为空**时才写，所以对着一个有真实数据的库跑它，不会追加资产、不会往已有履历里插东西；`link_monitors.py` 已经配好的会跳过，重跑第二遍不会重复绑定；`import_workstations.py` 以点位**编码**为准，重跑第二遍全部落「无变化」；`reset.py` 删的是资产 / 配对 / 履历 / 盘点 / 审计日志 / **点位**，**保留表结构和设备类型** —— 清完界面还能正常用，只是没有数据。

`reset.py` 默认先自动备份一份到 `backups\`（唯一后悔药），再要你亲手输入 `RESET` 才会动手；输错了、没输入、或者 stdin 是空的，一律中止。

### `import_workstations.py` 解决什么（⚠️ 全新 clone 的人先看这段）

它导入的是**一份固定的示例点位文件** —— 本项目自己办公室的点位。那份文件含真实员工姓名，**没有放进公开仓库**，所以你 clone 下来直接跑这条命令会看到"没有找到示例点位文件"，**这是正常的，不是你操作错了**。

> **建自己的地图，正确的顺序是**（全程 10 分钟内能完成，界面里就能做完）：
>
> 1. 启动服务，浏览器打开「空间地图」—— 第一次打开是一张**空白画布**，
>    上面有张卡写着怎么开始（系统不会替你猜办公室长什么样，这是故意的）。
> 2. 顶栏点「**编辑点位**」→ 点「新增」，再点画布空白处，就加了一个点位。
>    要排一片就点「**批量生成**」：填总数 / 起点 / 行列间距，能实时预览编号范围。
> 3. 想画房间和走廊，点「**编辑底图**」，从零画地台 / 走道 / 房间 / 墙体。
> 4. 资产在「资产台账」里逐台填「所在点位」，或者用「批量导入」一次导一批。
>
> 只有当**你手上已经有一份点位 JSON** 时才需要那个导入命令：
>
> ```
> python backend\import_workstations.py --file 你的文件.json
> ```

这条命令的规矩（用得上的话）：

- **默认只分析不写库**，必须加 `--yes` 才动手（与 `link_monitors.py` 同款，和 `reset.py` 相反）；
- 落库前**自动备份**，备份失败就不动手；
- **按点位编码 upsert**：库里没有就新增，有且字段变了就更新，完全一样就报「无变化」——
  所以同一份文件导第二遍是安全的，不会产生重复点位；
- **会显式忽略 JSON 里的 `assets` 字段**。有些点位文件里带一批演示资产
  （ThinkPad / Dell 之类），那是文件作者本地编的，跟真实 `assets` 表对不上任何编号 ——
  读进来会凭空造出一批假设备。真实资产挂在哪个点位，由资产自己的「所在点位」字段决定，
  不是由点位文件决定；
- **点位编码是唯一的，且删掉的点位不会释放编码**。所以别拿一个用过的编码去建新点位，
  会被告知「这个编码曾经用过」—— 这是为了让审计记录里两条同名点位不产生歧义。

**什么时候该跑它：** 首次上线把点位灌进库，或者数据库出问题后重建。
**日常调整点位（改人、改编码、拖动位置、增删）都在地图页面上做，不要重跑这条命令** ——
点位编码被人工改过之后，重跑会把它当成"新点位"再建一个。

### `link_workstations.py` 解决什么

它读点位文件里的人名，把其中「一台主机 + 一台显示器」的干净结构自动落到点位上（连带那两台设备），**其余一律不动** —— 0 台、2 台、只有笔记本/一体机的都会被跳过并列出来，你自己在系统里处理。
⚠️ 它同样依赖那份示例点位文件，**全新 clone 的库上没有它会直接找不到文件**；自己建地图的话直接在界面上填「所在点位」就行，不需要这条命令。

- 判据用的是**设备类别**（host / display），不是类型名 —— 你把「主机」改名成「机箱」也不影响；
  笔记本电脑、一体机的类别是「其他」，所以不会被误当成主机
- 只写**资产挂在哪个点位**，不碰主机↔显示器之间的配对关系（那是配对页的事）
- 已经挂过点位的设备**不会被覆盖**，所以重复跑是安全的
- **默认只分析不写库**，加 `--yes` 才动手，写入前自动备份

**什么时候该跑它：** 灌完点位数据之后。看干跑结果里列出的"跳过"名单，那些就是需要你手工处理的。

### `link_monitors.py` 解决什么

批量导入的资产里，显示器编号常常是「对应主机编号 + `-M`」，比如主机 `A100-01-00001` 配的显示器叫 `A100-01-00001-M`。几十上百台一台上界面点「绑定」不现实，这条命令按命名规则一次性关联完。它的规矩：

- **默认只分析不写库**，必须加 `--yes` 才动手（和 `reset.py` 相反：那边默认要确认词，这边默认连确认都不给，直接干跑）；
- 落库前**自动备份**，备份失败就不动手；
- 写入走的是界面同一套代码（校验、状态机、变更履历、审计日志全都有），审计按「一次批量操作记一条」的口径留痕；
- **只做加法**：显示器已经挂在别的主机上时**跳过并列出来**，不擅自换绑 —— 换绑会抹掉它以前的归属，这种决定留给人做；
- 任何一条写失败，**整批回滚**。

> 服务开着也能跑这两个命令（SQLite 单文件，不用停服务）。真遇到 `database is locked`，先跑 `stop.bat` 再试。
> 想看启动时自动灌（做演示 / 截图）：设 `IT_ASSET_SEED_ON_STARTUP=1`，别长期开着。

## 维护命令速查

| 想干什么 | 命令 |
| --- | --- |
| 装依赖（只需一次） | `python -m pip install -r backend\requirements.txt` |
| 看当前用的哪个 Python、缺什么包 | `python backend\check_env.py` |
| 起服务（不用脚本） | `cd backend && python run.py --port 18080` |
| 构建前端 | `cd frontend && npm install && npm run build` |
| 备份数据库 | `python backend\backup_db.py --keep 30` |
| 灌演示数据 | `python backend\seed.py` |
| 批量补主机↔显示器配对（按编号后缀） | `python backend\link_monitors.py --yes` |
| 灌入点位数据（资产空间地图） | `python backend\import_workstations.py --yes` |
| 自动关联「1 主机 + 1 显示器」到点位（先干跑） | `python backend\link_workstations.py` |
| 只读体检：关系差异 + 数据质量（不改数据） | `python backend\scan_relations.py` |
| 出「使用人非人名」清洗清单（不改数据，出 JSON + 可直接导入的 CSV） | `python backend\scan_relations.py --clean-plan .tmp\p0-clean` |
| 清空业务数据 | `python backend\reset.py` |

## [v2.8.0] — 2026-10-15

**主题：轻资产管理模块（批次 A · 底座）—— 不纳入正式台账的 IT 配件，也有地方管了**

### 起因

键鼠套装、SSD、内存、转接头这类东西不构成固定资产、没有正式编码，但**确实在流转**：
  
发给谁了、装在哪台机器上、拆下来放哪了，没人说得清。以前的出路只有两个：
  
塞进正式资产台账（污染统计口径，"150 台设备"从此说不清包不包括键鼠），
  
或者记在 Excel 里（与系统割裂，查不到、对不上）。

### 改动

新增独立的轻资产模块（`/api/light` 前缀、`/light` 页面），**三张新表、零迁移代码**
  
（全是新表，`create_all` 自动建；按外键依赖顺序登记进 `BUSINESS_TABLES` 即可被 reset 正确处理）：

- `light_categories` —— 品类：名称 / 品牌（选填）/ 规格（选填）/ 单位 / **追踪方式**（按数量 or 按单件）；
- `light_items` —— 单件档案：**只有按单件追踪的品类才建档**，序列号 + 标签，只建档不改变任何状态；
- `light_movements` —— **append-only 流水，全模块唯一真相**。每次流转追加一条，永不篡改。

核心口径（对应任务书核心规则 3 / 4 / 5 / 9 / 10）：

1. **当前状态全部从流水派生，不落库** —— 库存 = Σ 入库 − Σ 发出；单件"现在在哪" = 最后一条流水。
     
   界面上的每个数字都是后端现算的，前端一个数都不自己加。
2. **宿主信息现读，不复制** —— 配件关联正式资产后，"当前使用人 / 点位 / 状态"每次现读正式资产表。
     
   主机换人，配件的使用环境自动跟着变；历史流水里存的是**当时的编码快照**
     
   （`from_ref_code` / `to_ref_code`），资产删了历史还读得到，且不会指错对象
     
   （本库主键无 AUTOINCREMENT、id 会复用，只存 id 必然指错）。
3. **历史导入与期初初始化分离** —— `origin='import'` 只进历史、不进库存口径（批次 B 实现导入器）；
     
   `origin='opening'` 是盘点确认的真实基线，计入库存，**必须填操作人**。
     
   有分配却没入库的品类，台账显示「未登记入库」提示，**不推断真实库存**。
4. **操作语义按意图划分、互不重叠**（`LightOp.FLOWS`）——「分配」只对人、「安装」只对物。
     
   第一版两条都允许 `stock → X`，会出现"分配一台主机"这种语义上讲不通、但数据库照收的记录。
5. **更正 = 追加，不篡改** —— `POST /movements/{id}/reverse` 追加一条反向流水（分配错了就记归还），
     
   原记录一个字不改，两条通过 `corrects_id` 互相可追溯。报损没有机械反向（400），
     
   撤销它必须由人决定走哪条路，系统不替人做这个判断。

防呆：负库存 409（判据是"从库存发出"，安装也从库存走，漏掉它就能把库存装成负数）/
  
单件重复占用 409（声明的来源必须与它实际所在一致）/ 重复提交 409（`request_id`）/
  
占位符使用人（`/` 这类）不能当持有方 / 品类有流水后 `tracking` 锁定 409。

前端：顶栏「轻资产」入口，台账页（品类 + 派生统计 + 持有概况）+ 品类详情页
  
（持有明细 / 单件清单 / 流转流水三个页签）+ 三个对话框（品类 / 单件 / 登记流转）。
  
流转对话框的选项表是后端 FLOWS 的前端镜像，只为收窄选项，真正校验以后端为准。

### 测试

`backend/tests/test_light.py` **27 项全绿**（库存守恒 / 单件占用 / 负库存 / 重复提交 /
  
tracking 锁定 / 冲正 / 快照存活 / API 全流程 / 宿主搜索），后端全量回归 **115 项全绿**；
  
另跑真实 HTTP 服务端到端冒烟 **21 项全过**（临时库 + 8099 端口，覆盖任务书验收场景 1–6、9、10）。
  
**真实库未动**（150 台设备，无 light 表；测前已备份 `backups/it_assets_20261015_152239.db`）。

## [v2.7.2] — 2026-10-15

**主题：资产详情页显示「所在点位」—— 同一份数据在"看"的界面不能再缺一半**

### 起因

点位（`workstations`）是后加的一层。台账列表早就有「点位」列、地图整页都在按它摆，
  
但**资产详情页看不到它** —— 想确认"这台机器在哪一格"，只能打开「编辑」窗口。
  
问题的本质不是少显示一个字段：**同一份数据只在"改"的界面出现、在"看"的界面缺失**，
  
用户会合理地以为它是个可选字段，而它其实是台账的空间维度。

### 改动

- `AssetDetailView` 的「归属与维保」区块**第一项**加「所在点位」：
  - 显示点位编码（可点）→ 跳 `/map?station=<code>`，与问题中心「去核对」**同一个深链落点**，
      
    中途不再发明第二套跳转约定；
  - 一并显示**该点位使用人** —— 数据来自 `GET /api/workstations/{id}`（**与地图页同一个接口**），
      
    详情页不做任何本地拼装，避免"两套数据两处存"（本项目在决策 76 / 82 上已经吃过两次）；
  - 没挂点位时显示「未挂点位」，并说明去「编辑 → 所在点位」挂靠。
- 编码下方加一行小字区分「**所在点位**」（地图上的格子）与「**存放位置**」（自由文本备注）——
    
  两个字段同处一块，不说清用户会以为后者是前者的重复。
- 详情页内编辑保存后**重新拉一次点位**（编辑里可能刚改了所在点位，否则界面还显示旧格子）。
- 拉点位失败**不报错、不阻塞**：点位可能刚被删（`workstation_id` 残留旧值），
    
  此时详情页照常显示资产本身，只是那一行退回「未挂点位」—— 附属信息不该把整页打成错误页。

### 测试

浏览器 e2e **11 PASS**：字段出现 / 编码与使用人正确 / 可点击 / 点击后 URL 带 `?station=` 且地图选中该格 /
  
无点位时显示「未挂点位」且不渲染链接 / 无控制台报错。

## [v2.7.1] — 2026-10-15

**主题：清人方向补齐（关联操作建议第二期）+ 与迁移彻底解耦**

### 为什么只补「清人」这一个方向

先按真库（204 条审计）实测了四个候选场景，再决定做哪个：

| 场景            | 真库发生           | 单次收益 | 结论                                     |
| ------------- | -------------- | ---- | -------------------------------------- |
| **清人**（有人→无人） | 3 次            | 高    | ✅ **做** —— 唯一"事后没人兜底"的方向               |
| 换人（有人→有人）     | **0 次**        | 中高   | ⏸ 不做 —— 噪音高于收益（98% 一致率 → 一次弹 2 台且倾向全勾） |
| 绑定到有主点位       | 16 次 / 45 次改点位 | 低    | ⏸ 不做 —— 与问题中心重复，且命中率 ≈ 0.5%            |
| 迁移到有主点位       | **0 次**        | 低    | ⏸ 不做 —— v2.5.1 的迁移预览已承担该职责             |

判据固化为：**只在一个动作会让另一半事实"变得明显错误、或者变得看不见"时才提示。**
  
清人满足（点位清空后，设备上残留的名字**问题中心抓不到** —— `station_vs_asset_user`
  
要求两侧都有人、`asset_user_unregistered` 要求点位有人）；其余三个不满足。

### 实现

- `services/link_suggestions.py` 加 `suggest_clear_for_asset()` / `build_clear_suggestions()`：
    
  **只列使用人仍登记为被清那位的设备**（别人名下、本来空的一律不列）。
- 新增 `GET /api/workstations/{id}/unlink-suggestions`（预检，只读；点位无使用人 409）
    
  与 `POST /api/workstations/{id}/apply-unlink`（执行）。
    
  **接单不收人名** —— 清谁由服务端读点位当前使用人决定（不接受客户端指定，防清错人）。
- **清人默认一个都不勾**：它是"丢归属"方向，且设备可能属于岗位而非个人
    
  （人走了、机器留给下一任）。勾了才清，不勾就是保留。
- 执行前重检条件与填人相反：要求资产**仍登记为被清的那位**，否则跳过（`state_changed`）。
- 新审计 `asset_unlink`（🔓 解除使用人，归"点位与地图"组）；每台 1 条 `asset_events`。
- 前端 `LinkSuggestDialog` 支持 `mode: 'link' | 'unlink'`（导语 / 按钮 / 提示文案按方向切换）；
    
  `MapStationPanel.changeUser` 增加「有人 → 无人」预检分支。

### ⚠️ 与迁移解耦（用户口径："各干各的"）

两条路径互不调用：迁移的 `move_user` 走它自己的预览与令牌，清人建议只由
  
「用户在点位侧栏清空使用人」触发。解耦**不靠自觉** ——
  
`tests/test_link_suggestions.py::TestDecoupledFromRelocation` **读两个迁移模块的真实源码**，
  
断言其中不出现 `link_suggestions` / `build_clear_suggestions` / `apply-unlink`，
  
并断言迁移模块没有 `asset.user_name =`（迁移不碰资产使用人）。

### 测试

- 单测 **88 PASS**（+7：清人四分支 / 默认不勾 / 重检 / 解耦的**源码断言**）。
- 清人接口探针 **17 PASS**（只列该清的人 / 默认不勾 / 409 / 重检 / 审计 / 迁移预览未受影响）。
- 浏览器 e2e **27 PASS**（填人 16 + 清人 11，两个方向都走真实点击）。

## [v2.7.0] — 2026-10-15

**主题：关联操作建议（第一期）—— 从"有问题再提醒"到"操作之前先帮你想一步"**

不新建智能助手模块、不接 AI、不落库：在既有「点位编辑」入口上加一步**预检建议**。
  
与问题中心共用同一套归属口径（`ownership.has_owner()`），一个做事前、一个做事后。

### 第一期场景（仅此一个）

给**原本无归属**的点位新增使用人时（含空、`/`、`／`）：

| 资产现状                   | 建议                  | 默认勾选        |
| ---------------------- | ------------------- | ----------- |
| 没有使用人                  | `fill` 建议填入         | ✅           |
| 已是新使用人                 | **不进列表**（只提示有意义的变化） | —           |
| 有其他使用人                 | `conflict` 冲突（当前：X） | ❌ 不替用户做覆盖决定 |
| 公用 / 共享占位（公用/公共/共用/备用） | `keep` 可保留          | ❌           |

### 后端

- 新增 `services/link_suggestions.py`：纯函数建议引擎，`suggest_for_asset()` 是单台结论的唯一实现；
    
  **公用占位只在建议层认**，不动 `has_owner()` 全局口径（那是独立一轮决策）。
- 新增 `GET /api/workstations/{id}/link-suggestions`（预检，干跑，只读不写审计）：
    
  有人点位 409、占位符使用人 400；回包 `total = matched_count + len(suggestions)` 对账闭合。
- 新增 `POST /api/workstations/{id}/apply-linkage`（执行）：**保存前重新核对** ——
    
  弹窗期间资产被改过就跳过并回包说明（`reason: state_changed` / `not_on_station`），
    
  绝不拿过时结果批量覆盖；只处理真实挂在本点位的资产；只做"填人"不做"清人"。
- 每台资产 1 条 `asset_events`，一次操作 1 条新审计 `asset_linkage`（关联使用人 🤝，归"点位与地图"组）。

### 前端

- 新增 `LinkSuggestDialog.vue`：逐台勾选面板，全选 / 全不选 / 暂不处理 / 同步 N 台；
    
  文案（label / hint）由后端下发，前端一个字不拼；fill 蓝、keep 灰、conflict 琥珀 —— **建议不是告警，不用红**。
- `MapStationPanel.changeUser` 接线：仅「无归属 → 有人」方向预检；
    
  无建议项直接保存不弹；「换人（有→有）/ 清人」维持原行为不弹面板。

### 测试

- 单测 +10（`test_link_suggestions.py`）：四分支 / 排序 / 对账闭合 / ownership 一致性守卫 / 重检防护。**81 PASS**。
- 接口级探针 21 PASS（临时库：四分支、409/400 门、执行、过时数据防护、审计、问题中心联动）。
- 浏览器 e2e 16 PASS：面板出现 → 默认勾选状态 → 同步 → 数据/审计落库 → 换人不弹面板。

## [v2.6.0] — 2026-10-15

**主题：统一问题中心（Phase 3）+ 时间线补口（Phase 4）+ 数据卫生（Phase 0）**

### 一、问题中心（Phase 3）—— 检查引擎的一个**视图**，不是一张表

`GET /api/insights/issues`：**只读、不写审计、不落库**。全库五条规则现算：

| 规则                         | 触发                    | 严重                   | 动作落点                             | 真库体量（清洗前）    |
| -------------------------- | --------------------- | -------------------- | -------------------------------- | ------------ |
| `station_vs_asset_user`    | 点位使用人 ≠ 设备使用人（两侧都登记了） | review               | `/map?station=<code>`            | 2（均已被有效例外盖住） |
| `asset_user_unregistered`  | 点位有人、设备没登记使用人         | **info**（**不许判成错误**） | `/asset/<id>`                    | 4            |
| `asset_unbound`            | 资产没有点位                | info                 | `/?workstation=none`（**复用既有深链**） | 28           |
| `asset_on_deleted_station` | 资产挂在已删除的点位上           | review               | `/asset/<id>`                    | 0            |
| `relation_exception_stale` | 例外确认因关系变化而失效          | info                 | `/map?station=<code>`            | 0            |

**明确不进的**（这是"不变成红色告警墙"的保证，不是省略）：
  
点位没人但有主的设备（真库 10 个点位 —— **合法现状**）、字段完整度类问题
  
（真库 SN / 保修 **148/148 全空**，一进来就是 148 条）、未配对显示器（备案中）、
  
盘点任务开放太久（需阈值策略，属 Phase 5）、导入时的 warnings（不落库，不能当来源）。

**契约要点**（写进 CS 决策 83）：

- `key`（`<rule>:<scope>:<对象 id>`，只随**对象身份**变）与 `fingerprint`
    
  （随**关系状态**变，只用于判例外还算不算数）**分家**。拿 fingerprint 当标识，
    
  用户改一下使用人同一条问题就换了身份。
- 三个计数定义死：`by_rule.count`（含已确认例外）/ `handled_count` / `total = Σ(count - handled)`
    
  —— **已确认的例外不计入待办，但仍可查看、可撤销**。
- 排序**稳定**（`severity desc, rule asc, key asc`）—— 不然分页会漏条 / 重条。
- 动作 URL **只由后端规则模板生成**，且逐条过白名单（`ALLOWED_ACTION_PATTERNS`）；
    
  落点各不相同才给组级入口，否则只提供"展开逐条"。
- 输入校验：未知 `rule` / `severity` → **空集而不是 500**；`page_size` 夹到 `[1,100]`；
    
  `page` 夹到 ≥1。**不引入账号鉴权体系**（立项约束），这一条落到"输入校验 + 越权参数处理"。

**前端** `/insights`：三段式（一句话结论 → 规则卡"为什么值得关注" → 展开逐条"能做什么"）。
  
`review` 走**琥珀**、`info` 走**灰蓝**、**没有红色**；待办清零的卡收成中性色
  
（用琥珀强调一件没人要动手的事，等于教用户忽略琥珀）。空状态**明写"检查了什么"**
  
（N 条规则 / M 个点位 / K 台设备 + 规则清单）—— 否则空状态跟"功能坏了"长得一样。
  
导航新增「问题中心」（紧跟「资产台账」），角标**只在 `review > 0` 时**显示琥珀数字；
  
`SpaceMapView` 支持 `?station=<code>` 深链（复用页面已有的 `?task=` query 约定）。

### 二、时间线补口（Phase 4）

- `looks_like_place()` 补上"状态词"（`公用` / `公共` / `共用` / `备用`…）。
    
  **只在数据卫生层认，不动 `ownership.has_owner`** —— 引擎判"有没有人"的口径是决策 76 定的，
    
  改它会牵动前后端两份实现与既有 e2e，那是另一件事（理由写进函数注释）。

## [v2.5.1] — 2026-10-15

**主题：修掉「用起来才知道」的三处毛病 —— 两处是用户自己踩到的，一处是从他的报告里顺手挖出来的真缺陷**

### 1. 目标点位下拉不按编号排

用户在迁移对话框里挑目标点位"选择困难"。根因：候选直接用了 `GET /api/workstations` 的顺序，
  
而那是 **`y, x, id` = 地图渲染的顺序**（同一排的挨着给），放进一个"从 68 个点位里挑一个"的下拉就是
  
`W68, W69, W01, W02…`。

排序实现**本来就有** —— `utils/workstationMap.ts::compareStationCode`，`AssetFormDialog` 的点位下拉
  
一直在用（`W10` 排在 `W2` 前面正是它存在的理由）。**这个对话框漏用了，不是要新写一份。**
  
排序放在前端而不是改接口：`y, x` 顺序对地图是对的，动接口等于让地图迁就一个下拉的偏好。

### 2. 「没勾迁移使用人」时，界面从不告诉你「使用人没跟着走」

用户做了 `W46 → W47` 的「点位业务迁移 + 一并迁移设备」，执行完发现使用人没动，**去翻审计日志才看懂**。

后端一直是对的（审计里 `move_user: false` 白纸黑字），**错的是预览：它只说"会变的东西"，不说"不会变的东西"。**
  
于是：

- 预览新增常驻&#x7684;**「点位归属」块**：源、目标**两侧都把「迁移前 → 迁移后」摆出来**，不变的显式标「不变」；
- 新增结构化字段 `user_move` / `{source,target}_user_{before,after}` —— **勾没勾、甚至校验有冲突时都算出来**，
    
  界面不再靠文案猜；且这两侧的前后值**照实给原值**（含 `None` 与 `/`），显示统一走 `userLabel()`；
- 把 **`notes`（只说情况、不要求点头）** 与 `confirmations`（必须点头）分开 ——
    
  说清一件事不该顺手加一次确认负担，但那件事必须说出来。
- 复选框文案同步改准：`一并迁移设备（只搬设备；源点位 Wxx 上现有 N 台）`、
    
  `迁移点位使用人（…；源点位使用人会被清空。不勾就两侧都不动）`。

### 3. ⭐ 真缺陷：源点位使用人是 `/` 时，会把**目标点位的人覆盖掉**

`services/relocation.py` 判"有没有人"用的是自写的 `(user_name or "").strip()` —— **违反了决策 76**
  
（"有没有人"只认 `services/ownership.py::has_owner`）。后果不是显示问题，是**写坏数据**：

> 源点位 `user_name = "/"` → `strip()` 后仍是 `"/"`，真值 → 被当成**一个真使用人** →
>   
> 勾上「迁移点位使用人」执行 → **目标点位的「林晓薇」被写成 `/`**（归属丢失）。
>   
> 而同一份预览里还写着"源点位没有登记使用人，勾选「迁移使用人」实际不会改变任何东西" —— 文案与行为完全相反。

三处一起改：

| 位置                                        | 改动                                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| `services/relocation.py`（两个规划器）           | 判据换成 `has_owner()`：`/`、`／`、空值都算没归属                                         |
| `services/relocation.py`                  | 源点位没有归属 → 预览给**如实**的 `notes`（"没有归属可搬，目标现有的 X 保持不动"），不再冒那句不成立的 confirmation |
| `routers/relocation.py::apply_relocation` | **源点位真有归属才写** —— 拿"空"去覆盖目标不是迁移，是丢归属                                        |

行为口径（写进 CS 决策 82）：**"归属是否跟着走"是派生结果（`has_owner(源)` ∧ 勾了那一项），不是"勾没勾"本身**；
  
`plan.user_move` 与执行侧共用同一判据，预览与执行不会再各说一套。

### 验证

| ------------------- | ------------------------------------------------------------------------- |
| 纯函数单测               | **48 PASS**（`test_relocation.py` 18 → **22**，新增 `/`、全角 `／`、归属前后值、不覆盖目标四组） |

**主题：从「资产记录 + 关系展示 + 变更追溯」升级为「能主动指出关系差异、辅助点位迁移、支持就地处理」**

### P0：关系核对引擎 + 地图内联联动

**后端**（`services/relation_check.py`，**纯函数、零 IO**）

- 四种状态：`consistent` / `mismatch`（待核对）/ `unregistered`（未登记）/ `undetermined`（数据不足）。
    
  **没有 `error` 这个语义** —— 严重程度只有 `ok` / `info` / `review`。
- 三条规则：①两侧都登记了但不是同一个人 → `mismatch`（**待核对，不是错误**）；
    
  ②点位有人、挂着设备没登记使用人 → `unregistered`（提示账没填全）；
    
  ③**点位没人但有设备 → `unregistered`，文案里明写"这在业务上是正常的"**
    
  （公共设备 / 备用机 / 会议室机器都长这样）。
- `pair_state()` 抽出来给**核对与迁移预览共用** —— 两边各写一遍 if/else 迟早会漂，
    
  而漂的时候不会有任何报错，只是结论悄悄不一样。
- 指纹 `asset_fingerprint()` / `station_fingerprint()`：**关系一变指纹就变**，
    
  例外确认据此自动失效。指纹里带 `asset_code` 是因为主键非 AUTOINCREMENT、**id 会复用**。

**例外确认**（新表 `relation_exceptions`，唯一约束 `(rule, workstation_id, asset_id)`）

- 理由**必填**（没理由的例外等于把提示关掉）；重复确认就地更新。
- **软删不删行** —— "当初谁批的、后来怎么取消的"是历史。
- `asset_id` 用 **0 表示"点位级"**（不建外键，因为 SQLite 里 `NULL != NULL`，
    
  唯一约束对 NULL 不生效，会导致同一个点位能插无数条点位级例外）。
- 三条审计动作：`relation_exception_confirm` / `relation_exception_revoke` / `relocation_apply`。

**前端**（`components/RelationCheckCard.vue` + `MapStationPanel` 内联）

- **静默优先**：一致或没有可核对对象时只有一行浅灰文字，**不弹任何提示**。
- 差异走**琥珀不走红**，文案里明说"系统不会自动改任何一侧"。
- 差异在**资产行上就地标记**（「待核对」），一致的那几台不加任何装饰。
- 旧例外失效时显示"旧例外已失效"**并保留当时的理由**，差异重新露出来。
- ⚠️ **本轮自己踩到并修掉的一个坑**：例外确认后 `verdict` 仍是 `mismatch`（它算的是数据、不叠例外），
    
  概要文案落进 `switch` 的 default 分支，说出&#x4E86;**「两侧都没有登记使用人」这种与事实相反的话**。
    
  修法：概要里显式先判"差异是否已被有效例外盖住"，并给卡片加 `handled` 态（收成中性色）。
    
  **教训：派生值（verdict）与叠加层（例外）必须分开判断，不能让叠加层去猜派生值的意思。**

### P1：点位迁移助手

**独立路由 `/api/relocations`**（**刻意不并进 `/api/transfer`** —— 那个前缀是导入导出，
  
和"迁移"只是名字像；塞一起最坏会让人对着"迁移"按钮触发一次不可逆的批量导入）。

- `POST /preview` **纯读**；`POST /apply` 带**预览令牌**（并发改动与重复提交一条机制挡住，不符 → 409），
    
  **单事务**执行、任一步抛错整体回滚，返回受影响点位的**重算后**核对结果。
- **从不修改 `x` / `y`** —— 产物里刻意没有坐标字段，单测 `test_never_touches_coordinates` 钉住。
- **绝不自动推断使用人变更**：`mode=assets` 只改 `workstation_id`；`mode=station` 要不要搬使用人由用户勾。
- 预览里只**提示**迁移后会出现哪些差异，**不阻止**（合理差异不该拦住正常操作）。

**前端**（`components/RelocationDialog.vue`）：三步流程（选对象 → 预览 → 执行），
  
任何输入变化都让旧预览作废（免得照着旧清单点执行）；常驻文字写明"不动地图坐标，挪桌子请用「调整位置」"。

### 数据质量只读扫描（`backend/scan_relations.py`）

**只读**（`mode=ro` URI）、复用同一套规则、不重复实现；把全库分成
  
真实错误 / 合理差异 / 历史遗留 / 疑似误报四类，`--json` 出机器可读结果。
  
**没有、也不会用它批量改生产数据** —— 扫描结果的作用是反向检验规则的误报率。
